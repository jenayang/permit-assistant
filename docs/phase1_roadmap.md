# 프로젝트 로드맵 현황

> 이 문서는 원래 "Phase 1 MVP(2주 스프린트)" 일정표였다. 그 스프린트는
> 오래전에 끝났고 프로젝트는 그 이후 "서울시 건축 인허가 챗봇"에서
> "창업 로드맵 어시스턴트"로 스코프 자체가 커졌다 - 2026-07-28에 그 변화를
> 반영해 문서를 다시 썼다. 파일명(`phase1_roadmap.md`)은 히스토리 유지를
> 위해 그대로 뒀다.

**현재 목표**: 서울시 카페ᆞ음식점 등 소규모 창업의 전체 여정(행위 유형
확인→건축 인허가→공사→창업 행정→오픈 준비)을 안내ᆞ사전진단하는 챗봇.

- [x] 데이터 수집(건축법 3종 세트, 서울시 건축/도시계획 조례)
- [x] 카페 창업 3케이스(신축ᆞ용도변경ᆞ대수선) 시나리오 대응
- [x] 사전 진단 5항목(주차ᆞ정화조ᆞ소방ᆞ장애인 편의시설ᆞ위생) 자동 감지
- [x] RAG 인덱싱(청킹ᆞ벡터DB) + 기본 질의응답 파이프라인

## Phase 2: 판정 정확도 개선 + 부지 자동조회 (완료)

- [x] 규칙 기반 인허가 판정(`classify_case`) - 면적ᆞ층수ᆞ시설군 등 법령
      임계값을 LLM이 아니라 코드가 결정론적으로 계산
- [x] 구조화 출력(`PermitResult`) 도입
- [x] 부지 정보 자동 조회 - 용도지역(VWorld), 건폐율ᆞ용적률 법정 상한

- [x] LangGraph 체크포인터 SQLite 전환(서버 재시작 후에도 대화 상태 유지)

## Phase 3: 창업 로드맵 확장 (완료)

건축 인허가 판정 하나만으로는 실제 창업 과정을 다 못 담는다는 판단으로,
행위 유형 확인부터 오픈까지 전체 여정(Step 0~4)으로 스코프를 넓혔다.

- [x] 식품위생법상 영업 종류 판정(`classify_food_business`, 규칙 기반)
- [x] 소방시설 설치 대상 판정(`classify_fire_safety`, 규칙 기반)
- [x] 간판ᆞ옥외광고물 허가/신고 판정(`classify_signage`, 규칙 기반)
- [x] 공사(Step 2: 착공신고ᆞ설계ᆞ공사감리ᆞ사용승인) 안내
- [x] 사업자등록ᆞ위생교육 안내(정적 콘텐츠 → RAG 검색 기반으로 전환)
- [x] 오픈 준비(Step 4: 인테리어ᆞ장비설치ᆞ직원등록ᆞ영업시작) 체크리스트
- [x] 통합 로드맵 UI - 건축 트랙(순차)ᆞ창업 준비 트랙(병렬) 구분 표시,
      판정 축(체크 불가)ᆞ자기보고 축(체크박스) 구분, 선행조건 잠금(🔒)
- [x] 진행 현황 단일 계산 소스(`project_status.py`) - 재접속 요약ᆞNext
      Action 위젯이 서로 다른 진행률을 말하지 않도록
- [x] 답변 신뢰성 가드(`guard_node`) - 근거 없는 인용, 판정 전 단계 안내,
      단계 몰아주기, 기록 누락 등을 정규식+상태로 결정론적으로 검증
- [x] 건축물대장 도로명주소 지원(VWorld 지오코딩+역지오코딩) - VWorld
      장애 시 지번 전용 폴백으로 자동 전환
- [x] pytest 테스트 스위트 - 규칙 엔진 6종(허가/신고ᆞ식품위생ᆞ소방ᆞ
      간판) + guard_node/로드맵 상태머신 + 로드맵 잠금 규칙(93개, LLM
      호출 없이 결정론적으로 실행)

## 다음 우선순위 (현재 알려진 한계)

- **Gold Set 확대ᆞ반복 시행**: 지금 30건ᆞ케이스당 1회라 필드별 수치는 방향
  참고용이다("0%"가 1건 실패인 경우가 많음). Cerebras 측정은 30건 중 10건이
  호출 에러(레이트 리밋 추정)라 재측정 필요.
- **컨텍스트 — 로그 관찰 후 판단**: `[CONTEXT]` 경고가 자주 찍히면 요약 검토.
  다만 법령 근거를 요약하면 조문 번호가 뭉개지므로 신중할 것(자르는 건
  "없어지는" 거고 요약은 "틀리게 남는" 거라 성격이 다르다).
- **건폐율ᆞ용적률 - 도로폭 미반영**: 도로폭에 따른 완화 조항은 이번
  범위에서 제외했다. 별도 논의 후 반영 예정.
- **복합 행위 케이스 미지원**: 증축+용도변경처럼 두 행위가 동시에
  발생하는 케이스는 `case_facts`의 `act_type`이 단일 필드라 아직
  표현할 수 없다.
- **인용 근거(grounding) 최신성 창 좁히기**: `guard_node`가 "대화 전체
  기준 한 번이라도 검색했으면" 인용을 허용해서, 대화가 길어지면 이번
  턴에 실제로 검색 안 한 인용도 통과된다(알려진 트레이드오프로 남겨둔
  상태 - 좁히는 작업은 논의만 하고 보류 중).
- **로드맵 판정 축ᆞ체크 축 시각적 구분 강화**: 지금은 둘 다 리스트
  줄로만 보여서, 왜 어떤 항목은 체크되고 어떤 건 안 되는지 사용자가
  헷갈릴 수 있다 - 아이콘ᆞ범례 추가를 검토 중.
- **부모-자식 청킹 리팩터**: 현재 `law_chunker.py`ᆞ`parent_store.py`로
  직접 구현한 부모-자식 청킹을 LangChain의 `ParentDocumentRetriever`로
  교체 예정(동작은 동일하게 유지하고 유지보수성만 개선).
- **Rule Registry / Planner Agent**: 지금은 도메인별 규칙 엔진 6종을
  `DOMAIN_CONFIGS` 공통 파이프라인으로 관리 중이라 별도 레지스트리ᆞ
  플래너 없이도 충분하다고 판단 - 라우팅이 실제로 복잡해지는 시점이
  오면 재검토. (설계서의 Planner 전환을 보류한 배경은
  `project_report.md` 4-11 참고 - 대화형 UX와 충돌 가능성 때문)
- **guard 체크 커버리지 불균등**: 실측 사고 기반으로만 좁게 만들어져,
  아직 안 걸린 유사 사고가 다른 도메인ᆞ표현에 남아있을 수 있다(예:
  "착공"ᆞ"감리" 등 다른 표현으로 Step2를 RAG 없이 설명하는 경우는
  미포착). 같은 맥락에서 `tool_choice` 강제도 "지시는 있는데 강제는
  안 되는" 다른 전환 지점이 더 있는지 전수 조사한 적은 없다.
- **Answer 블록 도메인 분리**: 식품ᆞ소방ᆞ간판 전용 답변 규칙이 아직
  안 쓰여서 나눌 재료가 없다. 그 내용이 생기면 그때.
- **`prompts/*.md` 파일 분리**: 검토 후 보류. 프롬프트가 `agent.py`의
  14%뿐이고, 규칙과 그 근거 주석이 갈라지는 비용이 diff 가독성 이득보다
  크다고 판단.
