# 테스트 시나리오

`use_cases.md`가 "이런 대화를 지원한다"는 목표 정의라면, 이 문서는 그 목표가 실제로
지켜지는지 확인하기 위한 테스트 자료다. 두 파트로 구성:

- **Part A**: `classify_case()` 판정 로직 자체의 경계값 검증표 (모델 없이, 코드 레벨 확인)
- **Part B**: 다양한 사용자 페르소나·표현 방식을 가정한 대화형 시나리오 (모델 전체 파이프라인 확인)

새 케이스가 늘거나 규칙이 바뀌면 이 문서도 같이 갱신할 것 — 특히 Part A는
`src/tools.py`의 `REQUIRED_FIELDS`/`classify_case`와 항상 1:1로 맞아야 의미가 있다.

---

## Part A. `classify_case()` 경계값 검증표

`src/tools.py:classify_case()`가 법령 경계값을 정확히 나누는지 코드 레벨에서 먼저
검증한다. LLM 없이 바로 실행 가능:

```bash
python -c "
from src.tools import classify_case
print(classify_case({'act_type': '신축', 'size_sqm': 199, 'floors': 2, 'land_zone': '관리지역'}))
"
```

| # | act_type | 입력 case_facts | 기대 결과 | 경계 포인트 |
|---|----------|-----------------|-----------|-------------|
| 1 | 증축 | `extension_size_sqm=85` | 건축신고 | 85㎡ 이하 경계값 포함 |

| 17 | 용도변경 | `current_facility_group=7, desired_facility_group=5` | 용도변경허가 | 하위군→상위군(번호 감소) 이동 |
| 18 | 용도변경 | `current_facility_group=5, desired_facility_group=7` | 용도변경신고 | 상위군→하위군(번호 증가) 이동 |

| 25 | (없음) | `{}` | `None` | act_type조차 없는 최초 상태 |

## Part B. 대화형 시나리오 (다양한 사용자 유형)

각 시나리오는 **페르소나/표현 방식**, **대화**, **테스트 목적(모델이 무엇을 하거나
하지 말아야 하는지)**, **기대 판정**으로 구성. 실행은 `python -m src.pipeline
--query "..." --user <시나리오명>`으로 턴을 이어가며 확인 (같은 `--user`를 쓰면
체크포인터가 대화 이력을 유지함).

### B-1. 페르소나 다양성

#### 시나리오 6: 완전 초보자 — 신축 카페
**페르소나**: 건축 용어를 전혀 모르고, 정보를 뭉뚱그려 표현.
**대화**:
> "강남에 카페 하나 차리려고 하는데요, 건물을 새로 짓는 거예요. 한 20평 되고 2층짜리
> 건물이에요. 뭐부터 해야 하나요?"

**테스트 목적**: "20평"→㎡ 환산(약 66㎡), "새로 짓는다"→`act_type=신축` 매핑을
모델이 스스로 해내는지. `land_zone`이 안 나왔으므로 되묻는지, 아니면 임의로 가정하고
넘어가는지(넘어가면 안 됨 — `record_case_facts`가 채워지지 않으면 `classify_case`가
`None`을 반환해 아직 정보가 부족하다는 뜻).
**기대**: `land_zone`을 되묻고, 답변 전까지 "허가/신고"를 단정하지 않음.

#### 시나리오 7: 전문가(건축사) — 용도변경
**페르소나**: 법률 용어를 정확히 쓰고 정보를 한 번에 압축해서 줌.
**대화**:
> "제2종 근린생활시설(다중생활시설) 350㎡를 판매시설로 용도변경하려 합니다. 소유자
> 본인입니다. 절차 알려주세요."

**테스트 목적**: 전문 용어("제2종 근린생활시설 중 다중생활시설"은 영업시설군=5)를
`FACILITY_GROUPS` 매핑으로 정확히 번호화하는지. 사용자가 이미 소유자 여부까지
줬으므로 재차 owner_check를 묻지 않아야 함(대화 이력 확인 로직).
**기대**: `current_facility_group=5(영업시설군), desired_facility_group=5` — 어? 판매시설도
영업시설군이므로 실제로는 `건축물대장기재변경`이 나와야 정상. 이 시나리오는 일부러
"같은 시설군으로 착각하기 쉬운 사례"를 넣은 것 — 모델이 "이미 같은 시설군이라
허가/신고 없이 기재변경만 하면 됩니다"라고 정정해주는지가 핵심 체크포인트.

#### 시나리오 8: 정보를 찔끔찔끔 주는 사용자 — 대수선
**페르소나**: 한 번에 하나씩만 답하고, 되묻지 않으면 다음 정보를 주지 않음.
**대화(멀티턴)**:
1. "리모델링하려고 하는데 뭐 필요해요?"
2. (모델이 되물으면) "내력벽 하나를 없애려고요"
3. (모델이 되물으면) "연면적 180㎡, 2층이에요"

**테스트 목적**: `record_case_facts`가 매 턴 일부 필드만 채워도 이전 값이 안
지워지는지(`merge_facts` reducer 검증 — 코드 레벨로는 이미 확인했지만 실제 LLM
호출에서 누적되는지가 관건). 3턴 전부 끝나야 `renovation_scope=True, size_sqm=180,
floors=2`가 모여 `건축신고`로 판정됨.
**기대**: 3번째 답변 이후에야 `classify` 노드 진입, 그 전엔 계속 후속 질문만.

#### 시나리오 9: 결론만 원하는 사용자 — 신축
**페르소나**: 과정 설명 없이 바로 판정만 요구.
**대화**:
> "관리지역에 3층, 250㎡ 건물 지을 건데 그래서 허가야 신고야? 빨리 알려줘."

**테스트 목적**: 이번 리팩터링의 핵심 목적과 직결 — 사용자가 직접 "허가야 신고야"라고
캐물어도 모델이 즉석에서 대답을 지어내지 않고, 이미 준 정보(`size_sqm=250,
floors=3, land_zone=관리지역`)를 `record_case_facts`로 기록해서 규칙 기반 판정
결과(`건축허가`, 250㎡·3층이라 신고 요건 둘 다 불충족)를 다음 턴에 반영하는지.
**기대**: `건축허가`. 층수(3층)만으로도 이미 신고 요건 탈락이므로 오답 시 즉시
로직 버그로 간주.

#### 시나리오 10: 틀린 용어를 쓰는 사용자 — 용도변경
**페르소나**: 실존하지 않는 서류명/절차명을 확신에 차서 언급.
**대화**:
> "사무실을 카페로 바꾸는데 '용도변경 신고필증'이랑 '기재변경 허가서' 두 개 다
> 받아야 하나요?"

**테스트 목적**: 사용자가 만들어낸 잘못된 용어를 그대로 긍정하지 않고, 실제 절차
용어(용도변경 허가/신고, 건축물대장 기재변경)로 정정해서 안내하는지. 업무시설(8)→
근린생활시설(7) 이동이므로 `dst(7) > cur(8)`? 아니 8>7이므로 `dst<cur` → 용도변경허가.
**기대**: 오히려 사무실(주거업무시설군=8)→카페(근린생활시설군=7)는 번호가 8→7로
감소하므로 `용도변경허가` 대상이라는 정정 답변, 사용자가 말한 가상의 서류명은
자연스럽게 무시하고 정확한 절차명으로 대체.

### B-2. 행위 유형 커버리지 (기존 `use_cases.md`에 없던 유형)

#### 시나리오 11: 증축 — 옥상에 방 추가
> "옥상에 창고방 하나 늘리려고 하는데 늘어나는 면적이 40㎡ 정도예요."

**기대**: `extension_size_sqm=40 ≤ 85` → `건축신고`.

#### 시나리오 12: 재축 — 화재 소실 후 재건축
> "작년에 화재로 건물 일부가 타서 그 부분(120㎡)만 재축하려고 합니다."

**기대**: `extension_size_sqm=120 > 85` → `건축허가`. "재축"이라는 단어를 모델이
`act_type` 리터럴에 정확히 매핑하는지 확인(신축과 혼동하기 쉬움).

#### 시나리오 13: 이전 — 건물 통째로 이동
> "지금 건물을 대지 안에서 뒤쪽으로 이전하려고 해요. 크기 변화는 없어요."

**기대**: `이전`은 `REQUIRED_FIELDS=[]`라 규모 질문 없이 바로 `건축허가`. 모델이
불필요하게 면적/층수를 캐묻지 않는지가 체크포인트(과도한 질문 방지 테스트).

#### 시나리오 14: 가설건축물 — 공사현장 임시 컨테이너
> "공사 기간 동안 현장 사무실로 컨테이너 하나 놓으려고 하는데 인허가 필요한가요?"

**테스트 목적**: `temporary_purpose`를 "공사용"으로 매핑 → notice_purposes에 걸려
기간·구조 값이 없어도 `가설건축물신고`로 즉시 판정 가능한지(다른 act_type과 달리
목적만으로 조기 확정되는 특수 케이스).
**기대**: 존치기간/철콘 여부를 되묻지 않고 바로 `가설건축물신고` 안내.

#### 시나리오 15: 일반수선 — 사용자가 인허가가 필요하다고 착각
> "화장실 타일이랑 도배만 새로 하는 건데, 이것도 신고해야 하나요?"

**테스트 목적**: `일반수선`은 `인허가불필요`가 정답인데, 모델이 괜히 서류를
지어내거나 "간단하니 신고만 하면 됩니다" 식으로 존재하지 않는 절차를 만들어내지
않는지. 과잉 안내(hallucination) 방지 테스트.
**기대**: 별도 인허가 없이 진행 가능하다고 명확히 답변.

### B-3. 엣지케이스 / 적대적 테스트

#### 시나리오 16: 복합행위 — 증축 + 용도변경 동시 진행
> "창고를 20㎡ 늘리면서 동시에 그 창고를 카페로 바꾸려고 해요."

**테스트 목적**: 현재 `case_facts`는 `act_type` 필드가 하나뿐이라 두 행위를 동시에
표현할 수 없는 구조적 한계가 있음. 모델이 이걸 어떻게 처리하는지 관찰 —
① 하나만 골라 답하고 다른 하나는 누락하는지, ② 두 행위를 순차적으로 각각
안내하는지(가장 바람직), ③ 혼란스러워하며 뒤섞인 답을 주는지. **이 시나리오는
"정답이 없는" 스트레스 테스트에 가깝다** — 결과에 따라 `REQUIRED_FIELDS`/
`classify_case`를 복수 행위 지원 구조로 확장할지 판단하는 근거로 쓸 것.

#### 시나리오 17: 서비스 범위 밖 — 타 지역 질의
> "부산 해운대구에 카페 내려고 하는데 인허가 절차가 서울이랑 다른가요?"

**테스트 목적**: RAG 데이터가 서울시 조례 위주인데, 모델이 이 사실을 인지하고
"서울시 기준 데이터만 갖고 있다"고 명확히 고지하는지, 아니면 근거 없이 서울시
규정을 부산에도 그대로 적용해 답하는지(가장 위험한 실패 모드 — 근거 없는 지역
일반화).
**기대**: 국가 법령(건축법 본문 기준)은 답변 가능하되, 서울시 조례 관련 부분은
"서울시 기준"임을 명시하거나 타 지역은 확인 필요하다고 안내.

#### 시나리오 18: 소유자/임차인 답변 회피
> "그건 왜 물어봐요? 그냥 절차만 알려주세요." (owner_check 분기에서 답을 안 주는 경우)

**테스트 목적**: `owner_check`처럼 사용자만 답할 수 있는 분기 질문에 사용자가
답을 거부했을 때, 로드맵 진행이 멈추는지(강제로 아무 쪽이나 골라 진행하면 안 됨),
그리고 왜 필요한 정보인지(제출 서류가 소유자/임차인에 따라 다름) 한 번 더
설명해주는지.

#### 시나리오 19: 순수 정의 질문 — 도구 오발동 방지
> "근린생활시설이 정확히 뭔가요?"

**테스트 목적**: `[[project_tool_call_reliability]]` 이슈와 반대 방향의 리스크 —
이번엔 도구를 안 부르는 게 아니라 **불필요하게 `record_case_facts`를 호출**하는
과잉 반응을 테스트. 정의 질문은 `search_by_term`만 부르면 충분하고, 실제 창업/건축
계획이 언급되지 않았으므로 `act_type` 등을 추측해서 기록하면 안 됨.
**기대**: `search_by_term` 호출, `record_case_facts` 호출 없음.

#### 시나리오 20: 도구 호출 신뢰성 회귀 확인
> "동대문구에서 연면적 90㎡, 2층 카페를 신축하려고 하는데 관련 법 조항도 같이
> 알려주세요."

**테스트 목적**: `[[project_tool_call_reliability]]`에 기록된 기존 이슈(Gemini가
도구 호출을 통째로 생략하고 파라메트릭 지식으로만 답하는 문제)의 회귀 테스트.
`search_regulations`(법 조항 인용)와 `record_case_facts`(신축 판정용 사실 기록)
**둘 다** 같은 턴 또는 후속 턴에서 호출되는지 확인. 도구 호출 없이 답이 나오면
회귀 발생으로 간주하고 즉시 이슈 재오픈.

## 사용 방법 메모

- Part A는 `pytest` 없이도 즉석 `python -c`로 몇 초 안에 돌릴 수 있음 — 규칙을
  고칠 때마다 25개 행을 전부 재확인하는 습관을 들일 것.
- Part B는 Gemini 무료 티어 할당량(하루 20회, `src/config.py`)이 걸려있으므로
  한 번에 다 돌리지 말고, 그날 의심되는 부분(예: 새로 추가한 act_type, 최근 수정한
  프롬프트 문구) 위주로 3~5개만 골라 실행할 것.
- 시나리오 6, 9, 19, 20은 특히 "모델이 하지 말아야 할 행동"을 잡아내는 용도이므로,
  프롬프트나 그래프 구조를 바꿀 때마다 이 4개는 우선적으로 재검증.
