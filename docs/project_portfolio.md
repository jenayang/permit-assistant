### 01 프로젝트 소개 | 창업 로드맵 어시스턴트

서울시에서 카페ᆞ음식점을 차리려는 예비 창업자에게 "지금 뭐부터 해야 하는지"를
행위 유형 확인부터 건축 인허가ᆞ공사ᆞ식품위생 영업신고ᆞ소방ᆞ간판ᆞ사업자등록ᆞ
오픈 준비까지 전체 여정으로 안내하는 AI 에이전트예요.

- **참여 인원**: 1인 개발 ⚠️(팀 프로젝트였다면 알려주세요)
- **기간**: 약 2주 (2026-07-13 ~ 07-31, git 커밋 39개 기준) ⚠️("N개월"로 써야 하면 실제 기간 확인 필요)
- **기술 스택**: LangGraph(ReAct 에이전트) + FastAPI + ChromaDB(RAG) + Gemini/Cerebras

### 02 프로젝트 개요 | 배경과 목적

처음엔 "서울시 건축 인허가 챗봇"으로 시작했어요. 그런데 개발하면서 "카페 차리려는데
뭐부터 해야 해?"라는 사용자의 진짜 질문에 건축 인허가 판정만으로는 답이 안 된다는
걸 깨달았습니다. 실제 창업 과정은 건축 인허가 하나가 아니라 공사ᆞ식품위생 영업신고ᆞ
소방시설ᆞ간판ᆞ사업자등록ᆞ위생교육ᆞ오픈 준비까지 이어지는 하나의 여정이거든요.
그래서 스코프를 "인허가 판정 챗봇"에서 "창업 전체 여정을 안내하는 어시스턴트"로
넓히기로 방향을 잡았습니다.

### 03 진행한 일 | 배경 – 문제 – (핵심) – 해결

**배경**: 허가/신고 여부 같은 판정은 법령상 객관적 기준(면적ᆞ층수ᆞ시설군)으로
정해지는 값인데, 이걸 LLM에게 판단시키면 어떻게 될까?

**문제**: 실제로 시켜보니 두 가지 문제가 났어요.
1. LLM이 "허가 대상인가요, 신고 대상인가요?"를 사용자에게 되묻는 경우가 있었어요 —
   사용자가 애초에 알 수 없는 값을 되묻는 거라 대화가 막혔습니다.
2. 용도변경 방향(예: 시설군 8→7 이동) 같은 걸 LLM이 스스로 재추론하게 했더니,
   실제로 반대 방향으로 착각해서 말하는 사고가 재현됐어요.

**핵심 판단**: "법령상 객관적 기준으로 정해지는 판정은 LLM이 하지 않는다. 대신
파이썬 규칙 함수가 결정론적으로 계산하고, LLM은 그 결과를 사용자에게 설명하는
역할만 맡는다"는 원칙을 세웠습니다. 이 원칙을 프로젝트 전체(허가/신고 판정 →
식품위생 → 소방 → 간판, 총 4개 도메인)에 일관되게 적용했어요.

**해결**: `classify_case()` 등 6종 규칙 엔진 도입 + 25개 이상의 경계값 회귀
테스트로 고정. 용도변경 방향처럼 "왜 이 판정이 나왔는지" 설명도 LLM이 즉흥적으로
말하게 두지 않고, 이유 문장 자체를 코드가 결정론적으로 만들어 LLM에게 인용만
시키는 방식으로 확장했습니다.

### 04 과정 | 나의 직접적인 액션 + 인사이트

- **"프롬프트로 지시하면 되겠지"라는 가정을 실측으로 계속 검증했어요.** 시스템
  프롬프트에 "판정 후엔 필수 서류를 검색해서 답하라"고 지시해뒀는데도, 실제
  대화 로그를 열어보면 LLM이 도구 호출 없이 그럴듯하게 지어내 답한 사례가
  반복해서 나왔습니다. 이걸 보고 "안전-critical한 지점은 프롬프트가 아니라
  코드 레벨(그래프 노드)에서 사후 검증해야 한다"는 결론을 내리고 `guard_node`를
  설계했어요.
- **실사용 세션을 직접 복원해서 감사했어요.** "챗봇이 RAG를 잘 안 쓰는 것
  같다"는 문제의식이 들었을 때, 추측으로 답하지 않고 실제 대화가 저장된 SQLite
  체크포인트를 직접 열어 43개 메시지 전체를 재구성했습니다. 그 결과 "판정 직후
  20턴 넘게 검색이 단 한 번도 없다"는 구체적 증거를 확보했고, 이걸 근거로
  guard 체크를 하나 더 추가했어요.
- **가설을 세우고, 실험하고, 틀리면 인정하고 되돌렸어요.** 같은 문제(긴 대화에서
  도구 호출이 줄어드는 현상)를 고치려고 컨텍스트 트리밍을 구현했는데, 실제
  Gemini API로 A/B 테스트를 돌려보니 트리밍 유무와 무관하게 결과가 같았어요.
  "효과가 증명 안 됐다"는 걸 그대로 인정하고 롤백한 뒤, 다음 접근(tool_choice
  강제)으로 넘어갔습니다 — 되는 척 넘어가지 않고 실험 결과를 있는 그대로
  기록해두는 습관을 이번 프로젝트 내내 유지했어요.
- **문서와 코드가 어긋나 있는 걸 스스로 발견하고 바로잡았어요.** 아키텍처
  문서를 갱신하다가, "아직 정적 콘텐츠"라고 적어둔 부분이 실제로는 이미 RAG로
  전환되어 있다는 걸 코드 대조 중에 발견해서 정정했습니다. "일단 맞다고 가정하지
  않고 코드로 재확인한다"는 태도를 프로젝트 내내 유지했어요.
- **회귀를 막기 위해 고친 만큼 테스트를 같이 늘렸어요.** 버그를 고칠 때마다
  "왜 이 버그가 났는지"를 재현하는 테스트 케이스를 같이 추가해서, 테스트
  스위트가 0개에서 108개까지 늘어났습니다.

### 05 결과물 | 최종으로 진행한 내용 + 포인트

- 규칙 기반 판정 도메인 **4개**(건축 허가/신고/기재변경, 식품위생 영업신고,
  소방시설, 간판ᆞ옥외광고물) — 전부 결정론적 계산, LLM은 설명만 담당
- 답변 신뢰성 검증 노드(`guard_node`) — 근거 없는 법령 인용, 판정 전 단계
  안내, 기록 누락 등을 잡는 위반 체크 **6종**
- 대화 상태 SQLite 영구 저장 — 서버 재시작에도 세션 유지
- 정적 하드코딩 콘텐츠 **4종**을 검증 후 RAG 검색 기반으로 전환(법 개정 시
  재인덱싱만 하면 자동 반영)
- pytest 회귀 테스트 **108개**(전부 LLM 호출 없이 결정론적으로 실행)
- 통합 창업 로드맵 UI — 건축 트랙(순차)ᆞ창업 준비 트랙(병렬) 구분, 진행률
  단일 계산 소스

**핵심 포인트**: "판정의 정확성은 코드가 100% 책임지고, LLM은 그 결과를
사용자 상황에 맞게 설명ᆞ안내하는 역할에 집중한다"는 구조로 정리됩니다.

### 06 성장한 점 | 성과

- 판정 로직의 신뢰도를 **정성적 주장이 아니라 108개 회귀 테스트로 증명 가능한
  상태**로 만들었어요.
- guard_node 도입으로 "프롬프트 지시 → 그래프 레벨 강제 검증"이라는 패턴을
  확립했고, 이후 비슷한 문제(RAG 활용도 저조)가 생겼을 때 같은 패턴을 재사용해서
  훨씬 빠르게 대응할 수 있었습니다(체크 2개 → 5개 → 6개로 점진적 확장).
- 도메인이 1개(허가)에서 4개로 늘어나는 과정에서 "언제 추상화할지"를 미리
  기준(세 번째 도메인이 생기면 리팩터)으로 정해두고 실제로 그 시점에 실행해서,
  이후 도메인 추가가 코드 한 줄 등록으로 끝나는 구조를 만들었습니다.
- 컨텍스트 트리밍 실험처럼 **가설이 틀렸을 때 빠르게 인정하고 되돌리는 것도
  하나의 성과**로 남겼어요 — 매몰비용에 얽매이지 않고, 실험 자체를 문서화해서
  다음 시도(tool_choice 강제)의 근거로 남겼습니다.

이번 프로젝트를 하면서 "AI가 그럴듯하게 말하는 것"과 "실제로 맞는 것"은 다르다는
걸 계속 확인했습니다. 그래서 저는 새로운 기능을 추가할 때 주장이나 추측에 기대지
않고, 실제 로그ᆞ테스트ᆞ코드를 직접 열어서 근거를 확인한 뒤에 결정하는 방식으로
일합니다. 또한 안전-critical한 부분(이번 프로젝트에서는 법적 판정)은 확률적으로
동작하는 컴포넌트(LLM)에 맡기지 않고 결정론적으로 검증 가능한 구조로 분리해서
설계하는 걸 우선시합니다. 가설이 실험으로 틀렸다고 확인되면 미련 없이 되돌리고
다음 대안으로 넘어가는 것도 중요하게 생각해요. 입사 후에도 이런 방식으로, 겉보기에
동작하는 것과 실제로 신뢰할 수 있는 것을 구분해서 팀에 기여하고 싶습니다.
