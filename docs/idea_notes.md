## 진행 중인 최우선 과제 — 대화가 길어지면 tool-calling을 스킵하는 현상

**상태(2026-07-31): 부분 완화만 됨, 일반적 해결책 아직 없음.** 이게 지금 기술 개선
우선순위 1번. 지금까지 시도/검토한 것:

- `tool_choice` API 레벨 강제 — Step1→2 전환 지점(`_should_force_construction_guide`)
  **하나에만** 좁게 적용, 실측 성공. 하지만 이건 "그 지점"만 고친 것이지 일반적으로
  "대화가 길어지면 tool-calling이 준다"는 현상 자체를 고친 게 아님.
- 컨텍스트 트리밍(`_trim_tool_noise`, 최근 4턴만 유지) — 구현ᆞ단위테스트ᆞ실제
  Gemini 호출로 A/B 라이브 테스트까지 했으나 트리밍 유무로 tool-calling 성공률 차이가
  안 나타남 → 반증되어 전체 롤백함(`docs/project_report.md` 4-9 참고).
- guard_node 사후 체크(②③④⑤⑥) — 발생 "이후"에 잡아내는 안전망일 뿐, 애초에
  스킵을 막는 건 아님.

즉 지금 있는 방어선은 전부 "특정 지점 하나"나 "사후 교정"이지, 대화 길이 자체가
길어질 때 전반적으로 tool-calling 확률이 낮아지는 근본 원인에 대한 일반해는 아직
없음. 아래 체크리스트 검토(2026-07-31)도 이 문제를 계속 파고드는 맥락에서 진행함.

**새로 발견한 미해결 구멍(2026-07-31, 멀티턴 정확도 저하 연구 요약 검토 중 발견)**:
`merge_facts`(`agent.py:73-76`)는 `record_case_facts`가 다시 호출되기만 하면
필드 단위로 정확히 덮어써서 정정(correction)을 올바르게 처리한다 - 문제는 그
앞 단계. 유저가 "아까 85㎡라고 했는데 사실 100㎡야" 처럼 짧게 정정했을 때, 대화가

옛날 값이 그대로 남아 **잘못된 신고/허가 판정**으로 이어질 수 있음. 기존 guard
6개 체크 중 이걸 잡는 건 없음(⑥공사가이드 누락과 구조는 비슷하지만 대상이 다름).
**guard_node 7번째 체크(완료, 2026-08-01)**: 최근 유저 메시지가 정정 패턴(이미
기록된 case_facts 값과 다른 숫자 + "아니ᆞ정정ᆞ다시 말하면ᆞ아까" 류 키워드)인데
바로 다음 AI 턴에 `record_case_facts`가 호출 안 되면 위반 처리하도록
`_correction_omission_violations`(`agent.py`)로 구현. 정정할 기존 수치가 없거나

## CTDMate에서 가져올 만한 것 (기술 — 우선순위 후보, 코드로 검증됨)

## 외부 체크리스트 대조 (2026-07-31) — tool-calling 스킵 관련

사용자가 붙여넣은 컨설팅형 답변(LangGraph+Cerebras Gemma-4 tool-calling 스킵
체크리스트, 7개 항목)을 실제 `agent.py` 코드와 하나씩 대조한 결과.

1. **메시지 트리밍(최근 5~10개만 유지)** — 이미 시도함. `_trim_tool_noise`
   (최근 4턴만 유지)로 구현ᆞ단위테스트ᆞ실제 Gemini 호출 A/B 라이브테스트까지
   했는데 트리밍 유무로 tool-calling 성공률 차이가 없어서 반증ᆞ롤백함
   (`project_report.md` 4-9). **재확인 불필요.**
2. **RAG 컨텍스트를 최신 HumanMessage에 XML 태그로 감싸서 일회성 주입, 히스토리
   누적 금지** — **우리 아키텍처와 안 맞음.** 이 조언은 RAG 텍스트를 프롬프트에
   수동으로 꿰매 넣는 구식 구조를 전제로 함. 우리는 `search_regulations`/
   `search_by_term`이 진짜 LangChain 도구 호출이라 결과가 `ToolMessage`로
   쌓이는 게 정상적인 tool-calling 표준 동작임(모델이 자기가 뭘 검색했는지
   추적하는 데 필요). 이대로 적용하면 오히려 tool-calling 구조 자체를 깨뜨릴
   위험. **채택 안 함.**
3. **`tools_condition` 확인 + 키워드 감지시 강제 라우팅** — 우리는 prebuilt
   `tools_condition` 안 쓰고 커스텀 라우터(`route_after_agent` 등) 사용 중이라
   전자는 해당 없음. 후자(유저 발화에 "검색해줘"류 키워드 있으면 강제 라우팅)는
   지금 있는 `_should_force_construction_guide`(Step1→2 전환 지점 하나만
   좁게 커버)보다 **더 일반화된 버전** — 유일하게 새로 검토할 가치 있는 항목.
   CTDMate의 coverage-gated retry 아이디어와 같은 방향(좁은 지점 → 일반 조건).
4. **시스템 프롬프트 주기적 재주입** — 이미 하고 있음, 그것도 더 촘촘하게.
   `_roadmap_status_summary`+`permit_phase_directive`가 "길어지면"이 아니라
   **매 턴** 새로 계산돼서 최신 유저 메시지 바로 앞에 재주입됨. 체크리스트
   제안보다 이미 상위 구현. **추가 조치 불필요.**
5. **`tool_choice` 강제 호출** — 이미 이번 세션에 구현ᆞ실측 완료
   (`_should_force_construction_guide` + `bind_tools(tool_choice=...)`,
   Gemini/Cerebras 둘 다 검증). **이미 반영됨.**
6. **RAG 청크 개수/길이를 대화 후반부에 동적 축소** — 미구현, 미검증 가설.
   1번(메시지 개수 트리밍)과는 다른 축(정보 밀도)이라 완전히 같은 실험은
   아니지만, 1번이 반증된 것과 비슷한 "길이 때문일 것이다"류 가설이라
   우선순위는 낮게 둠. 나중에 여유 있을 때 검증 후보.
7. **자유 텍스트 전에 `{"call_tool": true/false}` JSON으로 먼저 판단시키기** —
   이미 있는 API 레벨 `tool_choice` 강제보다 원리적으로 약함(모델이 도구를
   빼먹는 것과 똑같은 이유로 이 JSON 판단도 빼먹을 수 있음). **채택 안 함.**

**결론**: 7개 중 실제로 새로 적용할 가치가 있는 건 **3번(유저 키워드 감지 →
tool_choice 강제 트리거를 일반화)** 하나뿐. 나머지는 이미 구현됐거나, 이미
실측으로 반증됐거나, 우리 tool-calling 아키텍처와 맞지 않음.

## 멀티턴 정확도 저하 연구 요약 대조 (2026-07-31)

사용자가 붙여넣은 글(단일턴 대비 멀티턴 최대 33% 정확도 하락, "주의력 분산"ᆞ
"의도 불일치" 원인, 실무 습관 4가지, MultiChallenge 벤치마크)을 실제 코드ᆞ
기존 실험 기록과 대조.

1. **신규 발견 — 정정 누락 guard 체크 후보**: 위 "진행 중인 최우선 과제" 섹션에
   상세 기록. 이번 검토에서 나온 가장 실질적인 소득 - 오분류 리스크로 직결되는
   미해결 구멍.
2. **"5~10턴마다 체크포인트" 습관** — `_roadmap_status_summary`+
   `permit_phase_directive`가 이미 **매 턴** 하고 있어 상위 구현. 추가 조치 불필요.
3. **"바뀐 조건은 교체로 선언"** — 이건 유저 발화 습관 가이드라 우리가 직접 통제할
   수 없음. 대신 상태 저장 레이어(`merge_facts`)는 이미 필드 단위 덮어쓰기라
   "교체" 의미론을 정확히 구현하고 있음을 확인(1번 항목의 전제가 됨).
4. **"대화 꼬이면 새 채팅으로 이사(요약 후 이관)"** — 기능 아이디어(요약 후 새
   세션 이관 UI)로 후순위 기록만. 백엔드 판정 로직과 무관.
5. **MultiChallenge류 다축 벤치마크(지시유지ᆞ사실기억ᆞ정정반영ᆞ자기일관성)** —
   방법론 개선 아이디어로 기록: 지난 컨텍스트 트리밍 실험은 실제 세션 1개를
   재구성한 1회성 A/B 테스트였는데, 이 글에 따르면 멀티턴 저하는 다수 시행에
   걸친 통계적 현상이라 단일 시행 검증은 신호가 약했을 수 있음. 앞으로 비슷한
   컨텍스트 관리 실험을 다시 한다면, 이 4개 축으로 나눈 작은 자체 회귀 테스트
   묶음(합성 멀티턴 시나리오 여러 개 + 각 축별 통과율)을 만들어서 검증하는 게
   1회성 A/B보다 신뢰도 높음. 미구현 - 실제 다음 실험 필요해질 때 꺼낼 것.

## legal-reviewer에서 가져올 만한 것 (기능 — 후순위, 미착수)

프론트 UI 장식 아이디어. 백엔드ᆞ판정 로직과 무관해서 착수 리스크는 낮지만, 지금
우선순위(기술 개선)에서 밀려 보류.

1. **입력 중 실시간 도메인 배지** — 사용자가 텍스트를 입력하는 동안(LLM 호출 전)
   클라이언트 단 키워드 매칭만으로 "감지된 도메인: 식품위생ᆞ소방" 같은 배지를
   즉시 보여줌(`onQI()`/`oninput` 패턴). 우리 쪽에도 `case_facts` 입력 중
   실시간 미리보기로 응용 가능.
2. **스트리밍 타이핑 커서 효과** — 답변이 스트리밍되는 동안 깜빡이는 커서를
   붙이는 순수 CSS/JS 트릭(`.scaret` + `caret` keyframe).
3. **답변 끝 고정 면책 문구** — "본 결과는 참고용 초안입니다" 같은 문구를 매
   답변 끝에 항상 붙이는 패턴. 우리는 guard_node라는 더 강한 기술적 안전장치가
   이미 있어서 우선순위는 낮지만, 사용자에게 "AI가 만든 참고용"이라는 기대치를
   텍스트로도 명시하는 건 저비용으로 더할 수 있음.
4. **공정-법규 매핑을 설정 탭에서 편집 가능하게** — 지금 우리 `permit_thresholds.yaml`은
   개발자만 고칠 수 있는데, 이 레포는 키워드↔법규 매핑 테이블을 UI에서 직접
   추가ᆞ수정하게 해뒀음. 비개발자가 도메인 매핑을 조정할 수 있게 하려면 참고할
   패턴이지만, 지금은 스코프 밖.

## legal-reviewer에서 반면교사로 확인한 것 (안 좋은 예시 — 우리가 이미 잘하고 있는 부분의 대조군)

- API 키를 브라우저 `localStorage`에 저장 + 직접 Anthropic API 호출(`anthropic-dangerous-direct-browser-access`) —
  키가 그대로 노출됨. 우리는 FastAPI 백엔드에서만 키를 다루는 게 맞는 설계임을 재확인.
- "조문을 정확히 인용하라"고 시스템 프롬프트로 지시하면서 실제 검색ᆞ근거 확보
  장치가 전혀 없음(PDF를 업로드해도 파일명ᆞ분류만 저장하고 내용은 안 읽음) —
  우리가 RAG + `guard_node`(인용 검증)로 막아온 문제의 정확한 반대 사례.
