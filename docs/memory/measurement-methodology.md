# 실측 방법론 — "A로 보였는데 실은 B였다"가 반복됐다

**원칙**: 외부 조언ᆞ가설을 그대로 수용하지 않고 코드ᆞ실측과 대조한 뒤
"이미 된 것 / 사실이 틀린 것 / 진짜 유효한 것"으로 갈라서 보고한다.

**규칙(CLAUDE.md §3과 동일, 여기가 배경)**:
- 변경 효과는 추정하지 말고 숫자로 전/후를 함께 측정한다.
- 유닛 테스트 통과로 만족하지 말고 실제 LLM 호출 스모크 테스트까지 한다.
- 원인이 애매하면 대조군(A/B)을 돌려 가린다.
- 한계ᆞ과대평가는 먼저 밝힌다(표본 1건이면 "0%"가 아니라 "1건 실패").

**하루에 세 번 반복된 패턴("A로 보였는데 실은 B")**:
1. tool-calling 스킵 — "대화가 길어서"로 보였지만 측정 자체가
   `pipeline.query()`(guard 재시도 포함)라 착시였다. [[tool-calling-reliability]]
2. 폴백 모델 크래시 — LLM이 정수를 문자열로 보내 규칙 엔진이 TypeError로
   죽던 것을 다른 원인으로 오인할 뻔함.
3. "컨텍스트 부족" — 실은 인덱스 미갱신으로 무관한 조문을 반환하던 것.
   [[context-budget-management]]

**측정 함정(가장 중요, 재발 방지)**: `pipeline.query()`로 tool-calling
호출률을 재면 안 된다 — 도구 루프ᆞclassifyᆞguard 재시도까지 도는 경로라
재시도가 성공을 가장한다. `llm.bind_tools(...).invoke()` 직접 1회 호출로
격리할 것(CLAUDE.md §4).

**공통 교훈**: 큰 설계(트리밍ᆞ요약ᆞ서브에이전트)로 바로 가지 말고, 먼저
관측ᆞ실측으로 진짜 원인을 좁힌다. 이 순서를 안 지켰으면 근본 원인을 두고
곁가지만 고쳤을 사례가 최소 3번.
