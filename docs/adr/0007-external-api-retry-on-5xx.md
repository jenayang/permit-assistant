# ADR-0007: 외부 정부 API(건축HUB)는 5xx에 한해서만 짧게 재시도한다

## Status

Accepted

> `docs/memory/external-api-reliability.md`, 커밋 `0c43e2f`를 바탕으로
> 재구성함.

---

## Context

건축물대장 조회(`lookup_building_ledger`, 공공데이터포털 건축HUB)가 실사용
중 500 Internal Server Error로 실패했다.

- 현재 상황: 재시도 로직이 없어 실패하면 바로 "직접 입력해달라"는 폴백으로
  넘어갔다.
- 해결해야 하는 문제: 같은 요청(주소ᆞ파라미터 동일)을 몇 초 뒤 그대로
  재실행하니 정상 200 응답이 오는 것을 직접 실측 확인했다 — 정부 API 쪽의
  일시적 오류로 보인다(코드 주석에도 이 API가 과거 다른 엔드포인트에서
  상시 500을 반환했던 이력이 이미 기록돼 있어, 이번에도 그 계열의
  불안정성으로 추정).
- 제약: 모든 실패를 재시도하면 4xx(서비스키ᆞ파라미터 오류처럼 재시도해도
  똑같이 실패하는 경우)까지 불필요하게 지연시킨다.

---

## Decision Drivers

- 실제로 몇 초 뒤 재실행하면 성공하는 걸 확인한 범위에만 재시도를 적용한다
  — 추측이 아니라 관측 기반.
- 재시도해도 결과가 달라지지 않는 오류(4xx)에 불필요한 지연을 추가하지
  않는다.

---

## Considered Options

### 1. 그대로 두고 실패 시 사용자에게 수동 입력 요청(기존 동작 유지)

재시도 로직 없이, 실패하면 바로 폴백 안내로 넘어가는 기존 동작을 유지.

**장점**
- 구현 비용이 없다.

**단점**
- 몇 초 뒤면 성공할 요청을 실패로 처리해 사용자에게 불필요한 수동 입력을
  요구한다 — 이미 실측으로 확인된 복구 가능한 실패를 방치하는 셈.

### 2. 5xx 응답에 한해 짧게 재시도

HTTP 5xx(서버 쪽 일시 오류)에 한해 1초 간격으로 1회 재시도하고, 4xx는
재시도 대상에서 제외하는 방식.

**장점**
- 실측으로 확인된 "일시적 오류 후 재시도 시 성공" 패턴을 그대로 흡수한다.
- 4xx(재시도해도 똑같이 실패)는 제외해 불필요한 지연을 방지한다.

**단점**
- 재시도가 발생하면 응답 지연이 최대 +1초 추가된다.
- 재시도해도 안 되면 결과적으로 기존과 동일한 폴백으로 끝난다(비용 대비
  효과가 제한적인 경우도 있음).

---

## Decision

**5xx 응답일 때만 1초 간격으로 1회 재시도한다. 4xx는 재시도 대상에서
제외한다.**

선택 이유: 같은 요청을 몇 초 뒤 그대로 재실행하면 정상 응답이 오는 것을
직접 실측했고, 이 API가 과거에도 비슷한 불안정성 이력이 있었다. 반면 4xx는
서비스키ᆞ파라미터 문제처럼 재시도해도 똑같이 실패하므로 지연만 추가하는
셈이라 제외했다.

---

## Consequences

### Positive

- 예전엔 실패하던 일시적 오류 케이스가 이제 재시도 한 번으로 성공한다 —
  사용자는 "예전엔 실패하던 케이스가 이제 성공한다"는 형태로만 체감한다
  (실패 경로 자체가 줄어듦).

### Negative

- 재시도 발생 시 응답 지연 최대 +1초.
- 재시도해도 안 되면 결과적으로 기존과 동일한 폴백 — 재시도가 실패 자체를
  없애주지는 않는다.

---

## Reconsideration Conditions

- 5xx 재시도 1회로도 복구되지 않는 빈도가 실제로 높게 관측되면(현재는
  측정 안 됨), 재시도 횟수ᆞ간격을 조정하거나 지수 백오프를 검토한다.
- 건축HUB 외 다른 외부 API(VWorld 등)에서도 비슷한 일시적 5xx 패턴이
  관측되면, 이 재시도 로직을 공용 유틸리티로 일반화하는 걸 검토한다.
