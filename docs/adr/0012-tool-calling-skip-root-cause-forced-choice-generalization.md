# ADR-0012: tool-calling 스킵은 프롬프트 문제가 아니라 도구 선택 층위의 문제였다 — 측정 설계를 바꿔 원인을 규명하고 `tool_choice` 강제를 전 도메인으로 일반화

## Status

Accepted

> 소급 작성 ADR — 2026-08-02 결정 당시 근거를 `docs/project_report.md` 4-12,
> 커밋 `41a0870`ᆞ`a58bc80`ᆞ`6f50e2b`를 바탕으로 재구성함. 이 프로젝트의
> "최대 미해결 과제"로 기록된 문제가 해결된 지점.

---

## Context

ADR-0009에서 컨텍스트 트리밍 시도 후 반증ᆞ롤백했고, 이후 `guard_node`
사후 검증(ADR-0003ᆞADR-0006)과 `tool_choice` 좁은 강제(ADR-0009)로 각각
부분 완화만 해둔 상태였다. 근본 원인(왜 특정 입력에서 도구 호출이
스킵되는가) 자체는 여전히 규명되지 않았다.

- 현재 상황: 지금까지는 `pipeline.query()`로 재현율을 측정했는데, 이건
  도구 루프ᆞ`classify`ᆞ`guard` 재시도까지 다 도는 경로라 (a) 시행당 LLM
  콜을 여러 번 써서 무료 티어 일 20회를 금방 소진하고 (b) **guard 재시도가
  두 번째 시도에서 도구를 부르면 마치 성공한 것처럼 보이는 착시**가 생긴다.
- 해결해야 하는 문제: 실제로 2026-08-01에 "어제는 실패했는데 오늘은
  성공"으로 보였던 게 바로 이 착시였다 — 측정 자체가 잘못됐다는 뜻.
- 제약: 측정을 먼저 고치지 않으면 어떤 가설을 검증해도 신뢰할 수 없다.

---

## Decision Drivers

- 측정 설계가 틀리면 어떤 실험도 무의미하다 — 가설 검증보다 측정 격리가
  먼저다.
- 가설은 전부 실측으로 기각ᆞ확인한다(추측으로 결론 내지 않는다).
- 안전-critical한 지점(기록 누락 시 판정 자체가 실패)은 모델의 확률적
  판단이 아니라 API 레벨 구조적 보장으로 막는다(ADR-0001ᆞADR-0003ᆞ
  ADR-0009와 같은 원칙).

---

## Considered Options

측정을 `llm.bind_tools(...).invoke()` 직접 1회 호출로 격리한 뒤
(시행당 정확히 1콜), 네 가지 가설을 조건별 실측(각 3회 반복)으로 검증했다.
각 가설이 "옵션"에 해당한다 — 어떤 원인론을 채택하느냐에 따라 대응 방식이
완전히 달라지기 때문이다.

### 1. "모델이 도구를 필수가 아니라 권장으로 다룬다"

**검증 결과: 확인됨.** `tool_choice` 강제는 두 입력 모두 100% 성공. 프롬프트에
"반드시 기록하라"를 여러 번 강화해도 안 고쳐지던 이유가 이것이다.

**이 가설을 채택했을 때의 대응**
- API 레벨에서 도구 호출을 강제하는 것 외에 다른 해법이 없다 — 프롬프트는
  구조적으로 무력하다.

### 2. "도구 수가 선택을 흐린다"

**검증 결과: 부분 확인.** signage(간판)는 15개→3개로 줄이자 0%→100%. 다만
food(식품)는 3개로 줄여도 0%라 도구 수만으로는 설명되지 않는다.

**이 가설을 단독 채택했을 때의 한계**
- 도구 수를 줄이는 것만으로는 모든 도메인의 문제를 해결하지 못한다 —
  부분적 설명일 뿐 충분조건이 아니다.

### 3. "질문형이면 답변 모드로 들어간다" / "긴 대화라서"

**검증 결과: 둘 다 기각.** 스킵된 두 입력 중 "카페 창업하려고요."는
서술형이다 — 어미와 무관하다. 전부 새 세션 첫 턴에서 재현돼, 애초에
길이가 원인이 아니었다 — ADR-0009의 트리밍 실험이 효과를 못 보인 이유가
이걸로 설명된다.

**이 가설들을 폐기한 이유**
- 실측 조건에서 반례가 명확하게 나왔다 — 더 이상 추적할 근거가 없다.

---

## Decision

**"모델이 도구를 권장으로 다룬다"가 근본 원인이라고 확정하고, `tool_choice`
강제(ADR-0009에서 `get_construction_guide` 하나에만 좁게 썼던 방식)를
`_forced_record_tool`로 확장해 모든 도메인에 일반화한다.**

선택 이유: 6개 조건 전부 3회 반복이 완전히 동일한 결과를 보여 **결정론적**
현상임을 확인했다 — 랜덤이 아니라 재현 가능하므로 회귀 테스트로 고정할 수
있었다. `DOMAIN_CONFIGS`(ADR-0004)에 `record_tool`ᆞ`keywords`를 추가해,
도메인이 늘어도 레지스트리 한 줄만 고치면 되도록 기존 패턴을 그대로
따랐다.

**강제 범위를 좁게 유지하는 세 조건**(무분별한 강제를 막기 위함):
① facts가 완전히 비었을 때만(도메인당 사실상 첫 기록 한 번)
② 이번 턴에 그 도구가 아직 안 불렸을 때만
③ 정의를 묻는 질문("건폐율이 뭐야")은 제외(기록할 사실이 없음)

**강제 범위의 경계(합의)**: 기록(`record_*`)은 강제하고, 검색
(`search_regulations` 등)은 모델 판단에 맡긴다 — 검색까지 강제하면
맥락 의존적 판단까지 규칙으로 못 박아 모델의 판단권이 과도하게 줄어든다.
기록은 유저가 이미 말한 사실을 적는 일이라 판단의 여지가 없고, 안 적으면
판정이 영영 안 되는 게 확정적이기 때문에 반대로 둔다.

## Consequences

### Positive

- 이 프로젝트의 최대 미해결 과제가 "프롬프트를 더 잘 쓰면 해결된다"가
  아니라 "도구 선택 층위의 문제"라는 게 실측으로 증명됐다 — 이후 비슷한
  문제에서 또 프롬프트 강화부터 시도하는 시행착오를 줄인다.
- 강제 판단을 구조화 로그(`[FORCED_TOOL]`ᆞ`[FORCED_TOOL_RESULT]`)로 남겨,
  "호출은 됐지만 추출은 실패"처럼 호출률과 추출 품질을 분리해서 볼 수
  있게 됐다.
- 회귀 테스트 9개(`tests/test_forced_record.py`)로 강제가 걸리는 자리와
  안 걸리는 자리를 양방향으로 고정했다.

### Negative

- 강제는 "유저가 도메인 키워드를 쓴 턴"에만 걸린다 — 키워드 없이 사실만
  흘리는 발화(예: "3층이고 200제곱미터예요")는 여전히 모델 재량이다.
- 강제된 호출에 모델이 값을 제대로 채우는지까지는 보장하지 못한다(호출
  자체만 보장) — 이건 다음 과제로 남았고, 위 로그가 그 측정의 입력이 된다.
- `guard_node`(사후 교정)와 `tool_choice`(사전 강제) 두 계층을 모두 유지해야
  해서 시스템 복잡도가 늘었다 — 다만 전자는 이미 벌어진 누락을 잡고 후자는
  애초에 벌어지지 않게 하는 역할이 달라 중복은 아니다.

---

## Reconsideration Conditions

- 키워드 없이 사실만 흘리는 발화에서도 기록 누락이 실제로 자주 관측되면,
  강제 조건에 키워드 외의 트리거(예: 사실 패턴 매칭)를 추가하는 걸 검토한다.
- `[FORCED_TOOL_RESULT] called=True args={}` (호출은 됐지만 추출 실패)
  빈도가 로그로 축적돼 유의미한 수준이면, 추출 품질 개선을 별도 과제로
  착수한다.
