# ADR-0009: 긴 대화 tool-calling 저하 — 컨텍스트 트리밍을 구현했다가 반증 후 롤백하고, `tool_choice` API 강제로 전환했다

## Status

Accepted

> 소급 작성 ADR — 2026-07-30~31 결정 당시 근거를 `docs/project_report.md` 4-9,
> `docs/memory/tool-calling-reliability.md`, 커밋 `0c43e2f`를 바탕으로
> 재구성함. **이 ADR은 한 번 구현까지 간 대안을 실측으로 반증하고 롤백한
> 뒤, 다른 대안으로 교체한 사례를 그대로 남긴다.**

---

## Context

ADR-0006에서 guard로 사후 방어는 추가했지만, 근본 원인(왜 대화가 길어지면
LLM이 도구 호출을 덜 하는가) 자체는 다루지 않은 상태였다.

- 현재 상황: 다른 오픈소스(`selltrat`)를 비교 검토했으나 멀티턴 에이전트
  루프 자체가 없는 스캐폴드 단계라 참고할 게 없었다.
- 해결해야 하는 문제: 업계에서 "lost in the middle"(긴 컨텍스트일수록 초반
  지시의 영향력이 옅어지는 현상)로 알려진 문제로 보고 접근했다.
- 제약: 판정 결과ᆞ사실은 이미 `case_facts`/`permit_result` 등 별도 state
  채널에 보존되어 있어, 오래된 원본 tool 메시지를 LLM 컨텍스트에 계속 들고
  있을 필요가 없다고 보는 가정에서 출발했다.

---

## Decision Drivers

- 가설이 아니라 **실측으로 증명된 인과관계**만 채택한다 — 토큰을 줄였다는
  사실만으로는 "버그를 고쳤다"고 주장하지 않는다.
- 되돌리기 쉬운 변경을 우선한다.
- 안전-critical한 지점은 확률적 개선이 아니라 구조적 보장으로 해결한다
  (ADR-0001ᆞADR-0003과 같은 원칙).

---

## Considered Options

### 1. 컨텍스트 트리밍 — 오래된 턴의 tool_call/ToolMessage 쌍 제거

LLM에 보내는 메시지 사본에서만(state 원본은 보존) 최근 4턴 이전의
tool_call/ToolMessage 쌍을 제거하고 HumanMessage+최종 텍스트만 남기는 방식
(`_trim_tool_noise()`).

**장점**
- 판정 결과는 별도 state 채널에 있어 오래된 tool 메시지를 지워도 로드맵
  정보 손실이 없다는 설계상 근거가 있었다.
- 토큰을 최대 43% 줄이는 효과가 확인됐다(부작용 없이).

**단점**
- **A/B 실험으로 반증됨**: 실제 세션(5db53ccb)을 재구성해 트리밍 ON(LLM
  전달 메시지 29개)ᆞOFF(51개) 두 조건으로 실제 Gemini를 호출해 비교했으나,
  두 조건 모두 `get_construction_guide`를 정상 호출 — 차이를 재현하지
  못했다. 대화 턴을 14턴까지 늘려도 동일했다.
- 단발 A/B는 LLM의 확률적 특성상 증거력이 약하다는 방법론적 한계도 확인됐다.

### 2. `tool_choice` 강제 — API 레벨에서 특정 조건에 도구 호출을 강제

특정 조건(Step1 끝ᆞconstruction_guide 미호출ᆞ직전 AI 메시지가 방금 Step2를
제안했고 사용자가 응답하는 턴)에서만 `llm.bind_tools(tool_choice=...)`로
그 턴만 새로 바인딩해 특정 도구 호출을 API 레벨에서 강제하는 방식.

**장점**
- `langchain_google_genai`ᆞ`langchain_cerebras`가 문자열 함수명으로 도구
  호출을 강제하는 기능을 실제로 지원함을 소스 코드로 확인했다.
- **라이브 검증 성공**: 트리밍 실험과 똑같이 재구성한 시나리오로 실제
  Gemini를 호출한 결과, 다른 텍스트나 다른 도구 호출 없이 정확히 그 도구만
  호출됨을 확인했다(`tool_calls: [('get_construction_guide', {})]`).
- 확률적 개선이 아니라 API 레벨 구조적 보장이라 실패 확률이 이론적으로
  0에 가깝다.

**단점**
- 강제된 턴에는 LLM이 다른 도구(예: 동시에 필요할 수 있는
  `record_case_facts`)를 같이 호출할 수 없다.
- 강제 범위를 조건 없이 넓히면, 사용자가 완전히 다른 주제를 물어봐도 매번
  공사 안내로 강제 전환되는 부작용이 생긴다 — 범위를 신중히 좁혀야 한다.

---

## Decision

**1차로 구현ᆞ실험까지 간 컨텍스트 트리밍은 롤백하고, `tool_choice` API
강제로 전환한다.**

선택 이유: 원 사고(turn 44)가 "길이에 비례해 확실히 나빠지는 현상"이라기보다
LLM의 확률적 변동(가끔 실수)에 더 가까울 가능성이 있다고 판단했다 — 트리밍
자체는 부작용 없이 토큰을 줄이는 효과는 확인했지만, "이 버그를 고쳤다"는
인과관계를 증명하지 못해 롤백했다. 실질적인 방어선은 트리밍보다 ADR-0006의
guard 체크일 가능성이 높다는 게 이 실험의 핵심 교훈이다.

`tool_choice` 강제는 `_should_force_construction_guide()`로 강제 범위를
"Step1 끝ᆞconstruction_guide 미호출ᆞ직전 AI 메시지가 방금 Step2를 제안했고
사용자가 그에 응답하는 턴"으로 좁혔다. 평소 경로의 캐싱된 `llm_with_tools`는
건드리지 않고, 그 턴만 새로 바인딩한다.

---

## Consequences

### Positive

- `tool_choice` 강제가 라이브 검증에서 100% 성공했다 — 확률적 개선이 아니라
  구조적 보장이라는 게 실측으로 확인됐다.
- 단위 테스트 5개 추가(강제 대상 판별 로직 - 제안 직후 응답ᆞ이미 호출됨ᆞ
  Step1 미완료ᆞ무관한 주제ᆞ직전 메시지가 사람이 아닌 경우), 전체 스위트
  113개 통과.
- "실측 없이 구조를 바꾸지 않는다"는 원칙이 트리밍 실험의 롤백으로 실제로
  지켜졌다는 걸 보여준 사례 — 이후 ADR-0014에서 이 전례를 근거로 다시
  언급된다.

### Negative

- 강제된 턴에는 LLM이 다른 도구를 동시에 호출할 수 없다 — 지금 범위
  (Step1→2 전환 시점)에선 문제가 안 되지만, 나중에 이 패턴을 다른 지점에
  적용할 땐 "그 턴에 정말 이 도구 하나만 필요한가"를 매번 확인해야 한다.
- 트리밍 실험 자체가 실제 Gemini API 호출(무료 티어 할당량)을 소모했다 —
  반증으로 끝난 실험의 비용.

---

## Reconsideration Conditions

- `tool_choice` 강제를 다른 지점에 추가로 적용하려 할 때, 그 턴에 동시에
  필요한 다른 도구 호출이 있는 경우가 발견되면 강제 범위ᆞ구현 방식을
  재검토한다.
- 컨텍스트 길이 자체가 다른 방식(예: 실제로 100턴 이상)으로 누적되는
  시나리오에서 다시 성능 저하가 관측되면, 트리밍을 "길이 때문"이 아닌 다른
  가설로 재실험할 수 있다 — 단, 이번 실험에서 길이 가설 자체는 반증됐다는
  점은 유지한다(ADR-0012에서 길이 가설이 재차 기각됨).
