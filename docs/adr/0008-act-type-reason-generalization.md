# ADR-0008: "왜?" 설명을 용도변경 하나에만 두지 않고 전체 act_type으로 일반화한다

## Status

Accepted

> 소급 작성 ADR — 2026-07-29 결정 당시 근거를 `docs/project_report.md` 4-8,
> 커밋 `0c43e2f`를 바탕으로 재구성함.

---

## Context

2026-07-24에 용도변경 방향(시설군 8→7군 이동) 오판 사고 이후, 그 도메인에만
`_facility_group_reason()`으로 결정론적 사유 문장을 도입했다.

- 현재 상황: 신축ᆞ증축ᆞ대수선ᆞ가설건축물 등 나머지 8개 act_type은 여전히
  LLM이 즉흥적으로 "왜 이 판정인지"를 설명해야 했다.
- 해결해야 하는 문제: 사용자가 "설명에 항상 근거가 붙었으면 좋겠다"고
  요청했다 — 용도변경만 근거가 결정론적이고 나머지는 LLM 재량이라는 비대칭이
  있었다.
- 제약: 기존 패턴(`_facility_group_reason`)이 이미 검증돼 있어, 확장 비용ᆞ
  리스크를 낮게 볼 수 있는 상황이었다.

---

## Decision Drivers

- 사용자가 명시적으로 요청한 일관성 — 모든 act_type에 같은 수준의 설명
  신뢰도가 있어야 한다.
- 이미 검증된 패턴을 재사용해 새로운 리스크를 만들지 않는다.

---

## Considered Options

### 1. 용도변경만 계속 특별 취급

나머지 8개 act_type은 그대로 LLM이 설명하게 두고, 용도변경만 결정론적
사유 문장을 유지하는 방식.

**장점**
- 추가 구현 비용이 없다.

**단점**
- 사용자가 지적한 비대칭이 그대로 남는다 — 왜 용도변경만 "근거가 있는
  설명"이고 나머지는 아닌지 설명하기 어렵다.

### 2. 같은 패턴을 전체 act_type으로 일반화

`_act_type_reason()`을 신규 추가해, 8개 act_type 전체에 결정론적 사유
문장을 적용하는 방식.

**장점**
- 이미 검증된 패턴(ADR-0001과 같은 "코드가 근거를 들고 있는다" 원칙)을
  재사용 — 새로운 리스크가 낮다.
- 사용자가 요청한 일관성을 전체 도메인에 걸쳐 충족한다.

**단점**
- 사유 문장의 비교 조건(예: "면적 < 200㎡")이 `classify_case()`의 실제
  판정 조건과 별도 위치에서 재비교되는 구조라, 나중에 조건 구조 자체가
  바뀌면 두 곳을 같이 고쳐야 하는 유지보수 리스크가 생긴다.

---

## Decision

**`_act_type_reason()`을 신규 추가해 8개 act_type 전체에 사유 문장을
적용한다.**

선택 이유: 사용자가 명시적으로 일관성을 요청했고, 기존 패턴이 이미 검증돼
있어 확장 비용ᆞ리스크가 낮다고 판단했다.

- 회귀 테스트 12개 추가(경계/예외 케이스 전부).

---

## Consequences

### Positive

- 전체 act_type에 걸쳐 설명 품질ᆞ신뢰도가 일관된다 — 기존 검증된 엔지니어링
  패턴의 재사용 사례.

### Negative

- 사유 문장의 비교 조건이 `classify_case()`의 실제 판정 조건과 별도 위치에서
  재비교되는 구조라, 법정 임계값이 아닌 조건 구조 자체가 바뀌면 두 곳을
  같이 고쳐야 하는 유지보수 리스크가 이론적으로 존재한다(숫자만 바뀌는
  개정은 `get_thresholds()` 공유로 안전).

---

## Reconsideration Conditions

- 사유 문장과 실제 판정 조건이 불일치하는 회귀가 실제로 발생하면(조건 구조
  변경 시 한쪽만 수정하는 실수), 두 로직을 단일 소스로 통합하는 리팩터를
  검토한다.
