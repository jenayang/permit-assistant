# ADR-0010: 시스템 프롬프트ᆞ도구 설명의 토큰을 실측하고, 인시던트 서사ᆞ중복 설명부터 제거한다

## Context

ADR-0009에서 대화 기록(message history) 길이는 트리밍으로 실험해봤지만,
대화 시작 전부터 매 턴 고정으로 나가는 시스템 프롬프트ᆞ도구 정의 자체의
크기는 검토한 적이 없었다.

- 현재 상황: `tiktoken`(cl100k_base)으로 실측한 결과, 매 턴 고정 오버헤드가
  `SYSTEM_PROMPT` 8,761 + 도구 15개 설명 7,614 + args 스키마 1,848 =
  **18,223토큰**이었다. 가이드 도구 4개를 한 번씩 다 호출하면(전체 로드맵
  완주 시) 누적 81,288토큰이 추가된다.
- 해결해야 하는 문제: Cerebras 폴백 모델의 컨텍스트 한도가 131,072토큰인데,
  고정 오버헤드+가이드 도구 누적만으로 전체 로드맵을 완주한 실제 대화
  하나가 12만~13만 토큰대에 도달할 수 있다 — 폴백의 하드 한도에 근접ᆞ초과할
  수 있는 실측 근거다. 트렁케이션 코드도 전혀 없어 한도를 넘으면 그냥
  provider API 호출이 실패한다.
- 제약: 가이드 도구가 큰 이유는 인시던트 서사가 아니라 정당한 법령 원문
  분량이다 — 콘텐츠 자체를 줄일 수는 없다.

---

## Decision Drivers

- 추정이 아니라 실제 코드에 로드된 값을 직접 토큰화해서 측정한다.
- 콘텐츠(법령 원문)와 군더더기(인시던트 서사ᆞ중복 설명)를 구분해서,
  콘텐츠는 건드리지 않고 군더더기만 제거한다.
- 모델별로 한도가 다르므로(Gemini 104만 vs Cerebras 13만) 폴백 모델 기준으로
  여유를 판단한다.

---

## Considered Options

### 1. SYSTEM_PROMPT·도구 docstring의 "개발자 인시던트 일지" 서사 제거

"실제로 겪은 문제 - 2026-07-27" 같은 날짜ᆞ세션ID 서사가 박혀있는 부분을
찾아 규칙(명령형 문장)은 유지하고 서사만 제거하는 방식.

**장점**
- 모델에 전송되는 텍스트에서 "왜 이 규칙이 생겼는지"라는, 모델 입장에서는
  불필요한 서사를 제거해 토큰을 줄인다.
- 이 배경은 `docs/project_report.md`와 각 코드 파일의 모듈 docstringᆞ주석에
  이미 남아있어 정보가 유실되지 않는다.

**단점**
- 절감폭 자체는 크지 않다(`SYSTEM_PROMPT` -284토큰) — 인시던트 서사보다
  규칙 본문(행동 지시)이 원래 분량의 대부분을 차지하고 있었다는 뜻.

### 2. 시스템 프롬프트와 도구 설명의 중복 제거

도구는 이미 각자의 `description`(함수 호출 스키마의 일부로 매 턴 전송됨)에
"언제 이 도구를 써야 하는지"를 상세히 담고 있는데, `SYSTEM_PROMPT`의
"도구 선택" 절이 같은 내용을 거의 동일하게 다시 서술하고 있었다 — 같은
지시가 두 곳에 중복 존재해 토큰을 이중으로 쓰는 구조.

**장점**
- 도구 docstring과 문장 단위로 거의 동일했던 4개 도구의 SYSTEM_PROMPT
  문단을 "도구 설명 참고" 한 줄 트리거로 축약해 실질적인 절감을 냈다.
- 여러 도구에 걸친 교차-도구 로직(예: "법 > 시행령 > 시행규칙 우선")은
  어느 한 도구의 description에도 못 넣으므로 그대로 남겨, 정보 손실이 없다.

**단점**
- 어느 부분이 진짜 중복이고 어느 부분이 도구 docstring에 없는 교차-도구
  로직인지 수작업으로 전수 대조해야 한다(예: `lookup_building_ledger`는
  앞부분만 축약하고 뒷부분은 그대로 남김).

---

## Decision

**두 조치를 순서대로 적용한다: (1) 인시던트 서사 제거, (2) 프롬프트-도구
설명 중복 제거.**

선택 이유: 콘텐츠(법령 원문)는 건드리지 않고 군더더기만 제거하는 게
원칙이었고, 실측으로 어느 쪽이 더 효과가 큰지 확인한 뒤 순서대로 적용했다.

- 조치 1 효과(실측): `SYSTEM_PROMPT` 8,761→8,477토큰(-284),
  `record_task_progress` 설명 약 -100여 토큰.
- 조치 2 효과(실측): `SYSTEM_PROMPT` 8,477→7,570토큰(-907, 약 10.7%).
  `tests/`(111개, LLM 호출 없음)로 회귀 없음 확인.

---

## Consequences

### Positive

- 콘텐츠 손실 없이 `SYSTEM_PROMPT`를 8,761→7,570토큰(약 13.6%) 줄였다.
- 가이드 도구가 큰 이유가 "콘텐츠 볼륨 문제"라는 걸 명확히 구분해, 다음
  조치(ADR-0011 조건부 프롬프트 조립)가 다른 각도(상태 기반 온ᆞ오프)로
  접근하는 근거가 됐다.

### Negative

- 조치 1의 절감폭은 크지 않았다(인시던트 서사가 분량의 대부분이 아니었음) —
  근본적으로 프롬프트를 줄이려면 다른 접근(ADR-0011)이 더 유효하다는 걸
  이 실측이 먼저 보여줬다.
- 가이드 도구 4개의 누적 반환값(81,288토큰)은 이 조치로 전혀 줄지 않았다 —
  별도 대응(재인덱싱 품질 문제, ADR-0013)이 필요했다.

---

## Reconsideration Conditions

- `SYSTEM_PROMPT`가 이후 다시 늘어나(새 규칙 추가 등) 비슷한 수준의 중복이
  재발하면, 같은 전수 대조 절차를 반복한다.
- 가이드 도구의 반환값 자체가 더 커지면(법령 추가 등), 콘텐츠 분량 문제를
  다시 실측하고 별도 조치(요약ᆞ분할 등)를 검토한다.
