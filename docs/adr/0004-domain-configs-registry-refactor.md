# ADR-0004: 도메인이 3개가 되는 시점에 `DOMAIN_CONFIGS` 레지스트리로 리팩터한다

## Status

Accepted

> 소급 작성 ADR — 2026-07-27 결정 당시 근거를 `docs/project_report.md` 4-4,
> `docs/memory/domain-registry-pattern.md`, 커밋 `e64e591`를 바탕으로 재구성함.

---

## Context

판정 도메인이 허가(1개)일 땐 `classify_node`/`route_after_tools`에 특별한
배선 문제가 없었다. 식품위생(2번째)ᆞ소방(3번째)까지 늘면서 도메인별 분기가
두 곳(라우팅 판단, 실제 처리)에 계속 늘어나는 구조가 됐다.

- 현재 상황: 새 도메인을 추가할 때마다 그래프 배선 코드 여러 곳을 동시에
  고쳐야 했다.
- 해결해야 하는 문제: 이대로 도메인이 늘면(실제로 이후 간판까지 4개, 더
  나아가 사업자등록ᆞ위생교육 등 RAG 가이드 도메인까지) 배선 코드의 분기
  수가 선형으로 늘어나 유지보수성이 나빠진다.
- 제약: 이 시점에 일반화 인프라를 미리 만들어두는 것과, 패턴이 실제로
  반복되는 걸 확인한 뒤 리팩터하는 것 중 선택이 필요했다.

---

## Decision Drivers

- 이 프로젝트의 원칙: "인프라를 먼저 일반화하지 않고, 콘텐츠(도메인)를 하나
  완성해보고 반복되는 패턴이 보이면 그때 리팩터한다"(2026-07-24 dev log에
  미리 명시된 원칙).
- 새 도메인 추가 비용을 "그래프 배선 수정"에서 "설정 한 줄 추가"로 낮추고 싶다.
- 리팩터 자체가 사용자에게 보이는 동작을 바꿔서는 안 된다(순수 유지보수 개선).

---

## Considered Options

### 1. 도메인이 늘 때마다 if문을 계속 추가

`classify_node`ᆞ`route_after_tools`에 도메인별 조건문을 그때그때 추가하는
기존 방식을 유지.

**장점**
- 리팩터 비용이 없다 — 당장은 가장 빠르다.

**단점**
- 도메인이 늘수록 두 곳(라우팅, 처리)에서 분기가 중복으로 늘어나 배선이 꼬인다.
- 새 도메인 추가 시 실수로 한쪽 분기만 고치는 회귀 위험이 커진다.

### 2. 공통 인터페이스로 추상화(레지스트리 패턴)

각 도메인이 `classify_fn`ᆞ키워드ᆞ상태 필드 등을 가진 설정 객체로 표현되고,
`DOMAIN_CONFIGS` 목록을 공통 파이프라인이 순회하며 처리하는 방식.

**장점**
- 새 도메인 추가가 "레지스트리에 설정 한 줄 추가"로 끝난다.
- 그래프 배선 코드를 안 건드리므로 회귀 위험이 줄어든다.

**단점**
- 추상화 설계ᆞ기존 도메인(허가ᆞ식품위생ᆞ소방) 이관에 리팩터 비용이 든다.
- 각 도메인의 `classify_fn`이 라우팅 판단과 실제 처리 두 곳에서 각각 호출돼
  약간의 중복 계산이 생긴다(순수 함수라 비용은 무시할 수준).

---

## Decision

**세 번째 도메인(소방) 추가 시점에 `DOMAIN_CONFIGS` 레지스트리로 리팩터한다.**

선택 이유: 2026-07-24 dev log에서 이미 "Rule Registry 분리는 세 번째 도메인이
생기면 판단한다"고 조건을 미리 정해뒀다 — "인프라를 먼저 일반화하지 않는다"는
원칙의 실제 적용 사례다. 패턴이 반복된다는 증거(2개 도메인에서 이미 분기가
꼬이기 시작)가 생긴 뒤에 리팩터했다.

---

## Consequences

### Positive

- 네 번째 도메인(간판) 추가는 그래프 배선 코드를 전혀 안 건드리고
  `DOMAIN_CONFIGS` 목록에 한 줄만 추가해서 완료됐다 — 리팩터 효과가 즉시
  다음 도메인에서 검증됨.
- 이후 `record_*` 강제 호출(ADR-0012)도 같은 레지스트리에 `record_tool`ᆞ
  `keywords` 필드를 추가하는 방식으로 확장돼, 패턴이 한 번 더 재사용됐다.

### Negative

- 각 도메인의 `classify_fn`이 라우팅 판단(`route_after_tools`)과 실제 처리
  (`classify_node`) 두 곳에서 각각 한 번씩, 총 두 번 호출되는 중복 계산이
  생긴다(순수 함수라 실질 비용은 무시할 수준이지만 구조적으로는 중복).

---

## Reconsideration Conditions

- 도메인 수가 더 늘어 레지스트리 설정 객체 자체의 필드가 과도하게 복잡해지면
  (현재는 `classify_fn`ᆞ키워드ᆞ`record_tool` 정도), 레지스트리를 더 세분화된
  구조로 재설계하는 걸 검토할 수 있다.
- 두 번 호출되는 중복 계산이 실제 성능 문제로 측정되면(현재는 순수 함수라
  무시할 수준), 호출 결과를 캐싱하는 방안을 검토한다.
