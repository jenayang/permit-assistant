# ADR-0002: 대화ᆞ판정 상태를 SQLite 체크포인터로 영구 저장한다

## Status

Accepted

> 소급 작성 ADR — 2026-07-24 결정 당시 근거를 `docs/project_report.md` 4-2,
> 커밋 `2a3dee4`를 바탕으로 재구성함.

---

## Context

LangGraph 에이전트는 체크포인터로 대화 상태(메시지 이력ᆞ`case_facts`ᆞ
`PermitResult` 등)를 관리한다. 초기 구현은 `InMemorySaver`를 썼는데, 이는
프로세스 메모리에만 상태를 들고 있다.

- 현재 상황: 서버가 재시작될 때마다(배포ᆞ코드 수정 후 재기동ᆞ장애 복구 등)
  모든 사용자의 대화ᆞ판정 상태가 전부 소실된다.
- 해결해야 하는 문제: 로드맵이 "세션 간 이어짐"으로 의미가 있으려면(오늘 인허가
  판정까지 받고, 다음 날 공사 단계로 돌아와도 처음부터 다시 묻지 않아야 함)
  상태 영속성이 선행되어야 한다.
- 제약: 이 시점(v0.4)에는 아직 도메인이 1~2개뿐이라 다른 기능 확장이 더
  눈에 띄는 선택지였지만, 나중에 도메인이 늘어날수록 되돌리는 비용이 커진다.

---

## Decision Drivers

- 세션 간 상태 유지가 이 프로젝트의 핵심 가치(로드맵)의 전제 조건이다.
- 별도 서버(DB 프로세스) 운영 부담을 늘리고 싶지 않다 — 로컬 배포 규모에
  맞는 선택이어야 한다.
- 다른 기능 확장보다 먼저 처리해야 나중에 "이미 쌓인 기능 위에 영속성을
  끼워 넣는" 리팩터 비용을 피할 수 있다.

---

## Considered Options

### 1. 지금은 미루고 다른 기능(도메인 확장)부터 진행

영속성 문제를 알고 있지만 당장 기능 확장(식품위생ᆞ소방 등 도메인 추가)이
더 급하다고 보고 나중으로 미루는 방식.

**장점**
- 단기적으로 체감되는 기능(새 도메인)이 더 빨리 늘어난다.

**단점**
- 도메인이 늘어날수록 "도메인별로 영속화해야 할 상태"가 늘어나 나중에 전환할
  때 되짚어야 할 범위가 커진다.
- 서버 재시작마다 상태가 사라지는 문제가 사용자 체감 품질을 계속 깎는다.

### 2. 지금 바로 DB 기반 체크포인터로 전환

도메인을 더 늘리기 전에 `SqliteSaver`로 전환해 영속성을 먼저 확보하는 방식.

**장점**
- 이후 추가되는 모든 도메인ᆞ상태가 처음부터 영속화된 기반 위에 쌓인다.
- 별도 DB 서버 없이 파일 기반(`chroma_db/checkpoints.sqlite`)으로 로컬 배포
  규모에 맞는 운영 부담을 유지한다.

**단점**
- 지금 당장 체감되는 새 기능은 아니다(인프라 투자).
- LangGraph 체크포인터의 직렬화 방식(msgpack)이 커스텀 Pydantic 모델을
  기본으로 지원하지 않아 추가 작업이 필요하다.

---

## Decision

**지금 바로 `SqliteSaver`로 전환한다.**

선택 이유: dev log(07-24)에 "나머지 기능이 '세션 간 이어짐'으로 의미가
있으려면 선행 필요"라는 원칙을 이미 세워뒀고, 이후 도메인이 늘어날수록
되돌리는 비용이 커지는 구조라 더 늦기 전에 처리하는 쪽을 택했다.

- `chroma_db/checkpoints.sqlite`에 체크포인트를 저장하도록 전환.
- 완전히 새 프로세스로 재기동해도 같은 `user_id`의 대화ᆞ판정 결과가 유지되는
  것을 직접 확인했다.

---

## Consequences

### Positive

- 서버 재시작(배포ᆞ장애 복구)이 더 이상 사용자 데이터를 지우지 않는다.
- 이후 추가된 모든 도메인(식품위생ᆞ소방ᆞ간판 등)이 처음부터 영속화된 상태
  위에서 동작해, 별도 전환 작업이 필요 없었다.

### Negative

- 체크포인터가 상태를 msgpack으로 직렬화하는데, `PermitResult`(커스텀 Pydantic
  모델)가 기본 직렬화기에 등록되지 않은 타입이라 경고가 발생했다. 전체 타입을
  허용하는 대신 이 타입 하나만 명시적으로 허용 목록에 등록해 해결했다(불필요한
  타입까지 역직렬화를 허용하지 않도록 범위를 좁힘).
- 파일 기반 SQLite라 다중 프로세스ᆞ수평 확장 환경에서는 별도 검토가 필요하다
  (현재 배포 규모에서는 해당 없음).

---

## Reconsideration Conditions

- 동시 접속ᆞ프로세스 수가 늘어 파일 기반 SQLite의 쓰기 동시성이 병목이 되는
  경우 — 그때 PostgreSQL 등 서버 기반 체크포인터로 재검토.
- 체크포인트 파일 크기가 무한정 누적되어 정리(retention) 정책이 필요해지는
  경우(현재는 다루지 않음, 미정).
