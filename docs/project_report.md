## 1. 프로젝트 개요

**무엇을 만들었나**: 서울시 카페ᆞ음식점 등 소규모 창업의 전체 여정(행위 유형 확인 →
건축 인허가 → 공사 → 식품위생ᆞ소방ᆞ간판ᆞ사업자등록ᆞ위생교육 → 오픈 준비)을 안내하는
LangGraph 기반 RAG 챗봇. 시작은 "서울시 건축 인허가 챗봇"이었고, 개발 중 스코프가
"창업 로드맵 어시스턴트"로 확장됐다.

**핵심 설계 원칙** (전 기간에 걸쳐 일관되게 적용됨):
- 허가/신고처럼 법령상 **객관적 기준으로 정해지는 판정은 LLM이 아니라 코드가 결정론적으로
  계산**한다. LLM은 판정 결과를 사용자에게 설명하는 역할만 맡는다.
- **"프롬프트 지시만으로는 안정성을 못 담보한다"**는 게 여러 차례 실측으로 확인되어,
  안전-critical한 지점은 전부 그래프 레벨(코드)에서 사후 검증하는 구조(`guard_node`)로
  옮겼다.
- 인프라를 먼저 일반화하지 않고, **콘텐츠(도메인)를 하나 완성해보고 반복되는 패턴이
  보이면 그때 리팩터**한다(2026-07-24 dev log에 명시된 원칙 — 실제로 도메인 3개째에서
  `DOMAIN_CONFIGS` 레지스트리로 리팩터됨).

## 4. 주요 Blocker 딥다이브

각 항목: 문제 → 검토한 대안 → 선택 이유 → 결과 → 트레이드오프 → 유형.

### 4-1. 허가/신고 판정을 LLM에 맡길 것인가, 코드로 뺄 것인가

- **문제**: 초기엔 "허가 대상인가요, 신고 대상인가요?"를 사용자에게 직접 묻거나 LLM이
  스스로 판단하게 했는데, 이건 애초에 사용자가 알 수 없는(법령상 정해지는) 값을 되묻는
  셈이었고, LLM이 계산을 틀리는 사례도 있었다.
- **검토한 대안**: (a) 프롬프트에 판정 기준을 상세히 서술하고 LLM 재량에 맡김, (b) 파이썬
  함수로 결정론적 계산 후 LLM은 설명만 담당.
- **선택 이유**: 법적 판정은 안전-critical하고 LLM의 확률적 오류를 허용할 수 없음.
- **결과**: `classify_case()` 등 6종 규칙 엔진 도입(허가/신고/기재변경, 식품위생, 소방,
  간판). 25개 경계값 회귀 테스트(`test_permit_classify.py`) 전부 통과.
- **트레이드오프**: 새 법령 개정이나 새로운 행위 유형이 생기면 규칙(if/elif) 자체를
  코드로 고쳐야 함 - 숫자만 바뀌는 개정은 YAML 분리로 흡수했지만, 조건 구조가 바뀌는
  개정은 여전히 코드 수정이 필요.
- **유형**: 기능적(정확한 판정이라는 사용자 가치) + 기술적(결정론적 로직 설계 결정).

### 4-2. 대화 상태 영속성 — 언제, 왜 지금 했는가

- **문제**: `InMemorySaver`라 서버가 재시작될 때마다 대화ᆞ판정 상태가 전부 소실.
- **검토한 대안**: (a) 뒤로 미루고 다른 기능부터 확장, (b) 지금 바로 DB 기반으로 전환.
- **선택 이유**: dev_log(07-24)에 명시 — "나머지 기능이 '세션 간 이어짐'으로 의미가
  있으려면 선행 필요"라는 원칙으로 다른 도메인 확장보다 먼저 처리.
- **결과**: `SqliteSaver`(`chroma_db/checkpoints.sqlite`)로 전환, 완전히 새 프로세스로
  재기동해도 같은 `user_id`의 대화ᆞ판정 결과가 유지되는 것을 확인.
- **트레이드오프**: 체크포인터가 상태를 msgpack으로 직렬화하는데 `PermitResult`(커스텀
  Pydantic 모델)가 기본 직렬화기에 등록 안 된 타입이라 경고가 발생 — 전체 허용 대신
  이 타입 하나만 명시적으로 허용 목록에 등록해서 해결(불필요한 타입까지 역직렬화
  허용하지 않도록 범위를 좁힘).
- **유형**: 기술(엔지니어링)적.

### 4-3. 프롬프트 지시의 한계 → `guard_node` 도입 (가장 중요한 전환점)

- **문제**: dev_log(07-24)에서 이미 "시스템 프롬프트에 지시를 강화했는데도 시설군 누락이
  재현된다 - 근본적으로는 LLM 신뢰성 이슈"라고 기록. 2026-07-26 세션에서는 판정 직후
  LLM이 여러 단계를 한 메시지에 몰아 공개하고, 사용자가 범위를 명시해도 무시하는 사고가
  실측으로 재현됨.
- **검토한 대안**: (a) 시스템 프롬프트를 계속 더 길게/강하게 작성, (b) 그래프 레벨에서
  자유 텍스트 답변을 사후 검증하는 노드 추가.
- **선택 이유**: "프롬프트 지시만으로는 못 막는다"가 반복적으로 실측 확인됨 — `classify_case`를
  코드로 뺀 것과 같은 논리를 대화 품질 검증에도 적용.
- **결과**: `guard_node` 도입 후 위반 체크가 2개(07-26) → 5개(07-28) → 6개(07-29)로
  계속 확장. 같은 턴 최대 1회 재시도로 무한 루프 방지.
- **트레이드오프**: 매 턴 정규식 기반 검증 오버헤드(경미), 위반 감지 시 응답 지연 +LLM
  재호출 1회. 그리고 이 프로젝트의 "실측 기반으로만 좁게 고친다" 원칙 때문에 **체크
  커버리지가 의도적으로 불균등** — 예를 들어 인용 검증(체크②)은 "대화 전체에 검색이
  한 번이라도 있었는지"만 보고 최신성은 안 따져서, 훨씬 이전 턴의 근거로 나중 턴의
  무관한 인용까지 통과되는 한계가 `phase1_roadmap.md`에 알려진 한계로 명시적으로
  남아있다(2026-07-29 기준 미해결, 의도적 보류).
- **유형**: 기술(엔지니어링)적 인프라, 사용자 체감 효과는 기능적(답변 신뢰성).

### 4-4. 도메인이 늘어날수록 배선이 꼬임 → `DOMAIN_CONFIGS` 레지스트리 리팩터

- **문제**: 판정 도메인이 허가 하나일 땐 괜찮았지만, 식품위생(2번째)ᆞ소방(3번째)까지
  늘면서 `classify_node`/`route_after_tools`에 도메인별 분기가 계속 늘어나는 구조가 됨.
- **검토한 대안**: (a) 도메인이 늘 때마다 if문 계속 추가, (b) 공통 인터페이스로 추상화.
- **선택 이유**: dev_log(07-24)에서 이미 "Rule Registry 분리는 세 번째 도메인이 생기면
  판단한다"고 조건을 미리 정해둠 — 실제로 3번째 도메인(소방) 추가 시점에 리팩터 실행.
  "인프라를 먼저 일반화하지 않는다"는 원칙의 실제 적용 사례.
- **결과**: 이후 4번째 도메인(간판) 추가는 그래프 배선 코드를 전혀 안 건드리고
  `DOMAIN_CONFIGS` 목록에 한 줄만 추가해서 완료.
- **트레이드오프**: 없음에 가까움(순수 개선) — 다만 각 도메인의 `classify_fn`이 라우팅
  판단(`route_after_tools`)과 실제 처리(`classify_node`) 두 곳에서 각각 한 번씩,
  총 두 번 호출되는 약간의 중복 계산이 생김(순수 함수라 비용은 무시할 수준).
- **유형**: 순수 기술(엔지니어링)적 — 사용자에게 보이는 변화 없음, 유지보수성만 개선.

### 4-5. 정적 하드코딩 콘텐츠 vs RAG 검색 — 언제 전환하는가

- **문제**: 사업자등록ᆞ위생교육ᆞ공사ᆞ4대보험 안내는 처음엔 관련 법령(부가가치세법,
  4대보험 관련법 등)이 인덱스에 없어서 원문 대조 후 정적 텍스트로 하드코딩했었다.
- **검토한 대안**: (a) 계속 정적 유지(법 개정 시 수동 재대조 필요), (b) 관련 법령을
  새로 확보ᆞ인덱싱해서 RAG로 전환.
- **선택 이유**: 법령을 실제로 추가ᆞ재인덱싱한 뒤 "정적 콘텐츠 vs RAG 비교 검증"을
  수행해, RAG가 정적 콘텐츠와 동일하거나 더 상세한 결론에 정확히 도달하는 걸 확인한
  뒤에만 전환 — 검증 없이 먼저 바꾸지 않음.
- **결과**: 4개 도메인 전부 RAG 전환 완료. 법이 개정되면 재인덱싱만 하면 자동 반영되고,
  원문을 다시 손으로 대조할 필요가 없어짐.
- **트레이드오프**: RAG는 검색 실패ᆞ환각 위험이 원천적으로 존재(정적 텍스트는 그
  위험이 없음), 매 호출마다 임베딩ᆞ검색 비용 발생. 법령 근거가 아예 없는 순수 실무
  체크리스트(인테리어ᆞ장비 설치, 영업 시작 항목)는 검색할 조항 자체가 없어 지금도
  의도적으로 정적 텍스트로 남겨둠 — "전환 가능한 것만 전환"이 원칙.
- **유형**: 기술적(검색 인프라 전환) + 기능적(법 개정 자동 반영이라는 사용자 가치).

### 4-6. RAG 활용도 저조 — 판정 시점에만 검색이 몰리는 문제 (2026-07-29 발견ᆞ해결)

- **문제**: 실제 세션(스레드 `5db53ccb`, 43개 메시지)을 SQLite 체크포인트에서 직접
  복원해 감사한 결과, `search_regulations` 호출이 판정 직후(turn 12~22)에만 3회
  몰려있고 이후 20턴 넘게 전혀 검색 없이 LLM 자체 지식으로 답변. 특히 Step 2(공사)
  안내를 전담하는 RAG 도구(`get_construction_guide`)가 정확히 그 내용을 설명하는
  순간(turn 44)에도 호출되지 않음 — 심지어 프롬프트(`permit_phase_directive`)에 이미
  "먼저 호출하라"는 지시가 있었는데도 무시됨.
- **검토한 대안**: (a) 시스템 프롬프트 지시를 한 번 더 강화, (b) `guard_node`에 위반
  체크를 하나 더 추가해 사후 검증.
- **선택 이유**: 4-3과 완전히 같은 논리 — 프롬프트 지시가 이미 있었는데도 무시된
  전례가 이번에도 그대로 재현되어, 프롬프트 강화만으로는 불충분하다고 판단.
- **결과**: `_construction_guide_gap_violations`(guard 6번째 체크) 추가. 회귀 테스트
  3개 추가(정상 호출 케이스ᆞ미호출 감지ᆞ무관 주제 오탐 방지).
- **트레이드오프**: 키워드 매칭("Step 2", "공사 단계")으로만 판별해서 오탐 방지 우선 —
  "착공"ᆞ"감리"ᆞ"사용승인" 같은 낱말은 Step1 요약에도 등장할 수 있어 일부러 체크
  대상에서 뺐다. 그만큼 더 넓은 표현으로 우회하는 경우는 아직 못 잡음(알려진 한계).
- **유형**: 기술(엔지니어링)적(guard 인프라 확장), 사용자 체감은 기능적(답변 품질ᆞ
  RAG 활용도).

### 4-7. 외부 정부 API(건축HUB) 순간 오류 — 재시도 로직 부재 (2026-07-29 발견ᆞ해결)

- **문제**: 건축물대장 조회(`lookup_building_ledger`)가 실사용 중 500 Internal Server
  Error로 실패, 재시도 로직이 없어 바로 "직접 입력해달라"는 폴백으로 넘어감.
- **검토한 대안**: (a) 그대로 두고 실패 시 사용자에게 수동 입력 요청(기존 동작 유지),
  (b) 5xx 응답에 한해 짧게 재시도.
- **선택 이유**: 같은 요청(주소ᆞ파라미터 동일)을 몇 초 뒤 그대로 재실행하니 정상 200
  응답이 오는 것을 직접 실측 확인 — 정부 API 쪽의 일시적 오류로 판단(코드 주석에도
  이 API가 과거 다른 엔드포인트에서 상시 500을 반환했던 이력이 이미 기록돼 있어,
  이번에도 그 계열의 불안정성으로 추정).
- **결과**: 5xx 응답일 때만 1회(1초 간격) 재시도하도록 추가. 4xx(서비스키ᆞ파라미터
  오류처럼 재시도해도 똑같이 실패하는 경우)는 재시도 대상에서 제외해 불필요한 지연을
  방지.
- **트레이드오프**: 재시도 발생 시 응답 지연 최대 +1초, 재시도해도 안 되면 결과적으로
  기존과 동일하게 폴백.
- **유형**: 순수 기술(엔지니어링)적 — 신뢰성/안정성 개선, 사용자에게는 "예전엔 실패하던
  케이스가 이제 성공한다"는 형태로만 체감됨.

### 4-8. "왜?" 설명이 용도변경에만 있던 비대칭 해소 (2026-07-29)

- **문제**: 2026-07-24에 용도변경 방향(8→7군 이동) 오판 사고 이후 그 도메인에만
  `_facility_group_reason()`으로 결정론적 사유 문장을 도입했는데, 신축ᆞ증축ᆞ대수선ᆞ
  가설건축물 등 나머지 8개 act_type은 여전히 LLM이 즉흥적으로 "왜"를 설명해야 했다.
- **검토한 대안**: (a) 용도변경만 계속 특별 취급, (b) 같은 패턴을 전체 act_type으로
  일반화.
- **선택 이유**: 사용자가 "설명에 항상 근거가 붙었으면 좋겠다"고 요청, 기존 패턴이
  이미 검증돼 있어 확장 비용ᆞ리스크가 낮다고 판단.
- **결과**: `_act_type_reason()` 신규 추가, 8개 act_type 전체에 사유 문장 적용.
  회귀 테스트 12개 추가(경계/예외 케이스 전부).
- **트레이드오프**: 사유 문장의 비교 조건(예: "면적 < 200㎡")이 `classify_case()`의
  실제 판정 조건과 별도 위치에서 재비교되는 구조라, 나중에 법정 임계값이 아닌 **조건
  구조 자체**가 바뀌면 두 곳을 같이 고쳐야 하는 유지보수 리스크가 이론적으로 존재
  (숫자만 바뀌는 개정은 `get_thresholds()` 공유로 안전).
- **유형**: 기능적(설명 품질ᆞ신뢰도) — 기존 검증된 엔지니어링 패턴의 재사용.

### 4-9. 긴 대화에서 tool-calling 저하 — 컨텍스트 트리밍 시도 후 롤백 (2026-07-30~31)

- **문제**: 4-6에서 guard로 사후 방어는 추가했지만, 근본 원인(왜 대화가 길어지면
  LLM이 도구 호출을 덜 하는가) 자체는 안 건드린 상태였다. 다른 오픈소스(`selltrat`)를
  비교 검토했으나 멀티턴 에이전트 루프 자체가 없는 스캐폴드 단계라 참고할 게 없었고,
  업계에서 "lost in the middle"(긴 컨텍스트일수록 초반 지시의 영향력이 옅어지는 현상)로
  알려진 문제로 판단.
- **검토한 대안**: (a) 컨텍스트 트리밍 — 오래된 턴의 tool_call/ToolMessage 쌍을 LLM에
  보내는 사본에서만 제거(state 원본은 보존), (b) `tool_choice` 강제 — 특정 조건에서
  LLM이 도구 호출을 건너뛸 수 없게 API 레벨에서 강제.
- **선택 이유(1차 시도, a)**: 판정 결과ᆞ사실은 이미 `case_facts`/`permit_result` 등
  별도 state 채널에 보존되어 있어, 오래된 원본 tool 메시지를 LLM 컨텍스트에 계속 들고
  있을 필요가 없다고 보고 상대적으로 구현 비용이 낮은 (a)부터 시도.
- **구현**: `_trim_tool_noise()` — 최근 4턴 이전은 tool_call/ToolMessage 쌍을 제거하고
  HumanMessage+최종 텍스트만 남김. 단위 테스트 5개 전부 통과(쌍 제거 정확성ᆞ최근 턴
  보존ᆞorphan tool_call 없음ᆞ원본 불변 등 검증됨).
  **A/B 실험 결과**: 실제 세션(5db53ccb)을 재구성해 트리밍 ON(LLM 전달 메시지 29개)ᆞ
  OFF(51개) 두 조건으로 실제 Gemini를 호출해 비교했으나, **두 조건 모두
  `get_construction_guide`를 정상 호출** — 차이를 재현하지 못함. 대화 턴을 14턴까지
  늘려도 동일.
- **결론ᆞ롤백 이유**: 원 사고(turn 44)가 "길이에 비례해 확실히 나빠지는 현상"이라기보다
  LLM의 확률적 변동(가끔 실수)에 더 가까울 가능성이 있다고 판단 — 트리밍 자체는
  부작용 없이 토큰을 최대 43% 줄이는 효과는 확인했지만, "이 버그를 고쳤다"는 인과
  관계를 증명하지 못해 롤백했다. 실질적인 방어선은 이 트리밍보다 4-6의 guard 체크일
  가능성이 높다는 게 이번 실험의 핵심 교훈.
- **트레이드오프**: 실험 자체가 실제 Gemini API 호출(무료 티어 할당량)을 소모함 - 단발
  A/B는 LLM의 확률적 특성상 증거력이 약하다는 방법론적 한계도 확인.
- **유형**: 기술(엔지니어링)적 실험 — 이번엔 명확한 결과 없이 "가설 기각"으로 끝났고,
  그 자체를 기록해두는 것도 과정의 일부로 남긴다.

**→ 2차 시도(대안 b) — `tool_choice` 강제, 성공**: `langchain_google_genai`ᆞ
`langchain_cerebras`의 `bind_tools(tool_choice=...)`가 특정 함수명을 강제 호출시키는
기능을 실제로 지원함을 소스 코드로 확인(둘 다 문자열 함수명 → 내부적으로 정규화).
`_should_force_construction_guide()`를 추가해, "Step1 끝ᆞconstruction_guide
미호출ᆞ직전 AI 메시지가 방금 Step2를 제안했고 사용자가 그에 응답하는 턴"으로만
강제 범위를 좁혔다(조건 없이 전체 구간에 강제하면 그 구간에 사용자가 완전히 다른
주제를 물어봐도 매번 공사 안내로 강제 전환되는 부작용이 생기기 때문). 이 조건일 때만
`llm.bind_tools(TOOLS, tool_choice="get_construction_guide")`로 그 턴만 새로
바인딩해서 호출한다(평소 경로의 캐싱된 `llm_with_tools`는 안 건드림).
**라이브 검증 결과**: 트리밍 실험과 똑같이 재구성한 시나리오로 실제 Gemini를
호출한 결과, `tool_calls: [('get_construction_guide', {})]` — 다른 텍스트나 다른
도구 호출 없이 정확히 그 도구만 호출됨을 확인. 단위 테스트 5개 추가(강제 대상
판별 로직 - 제안 직후 응답ᆞ이미 호출됨ᆞStep1 미완료ᆞ무관한 주제ᆞ직전 메시지가
사람이 아닌 경우), 전체 스위트 113개 통과.
- **1차(트리밍)와의 차이**: 트리밍은 "LLM이 지시를 더 잘 따르길 기대"하는 확률적
  개선이었던 반면, 이건 API 레벨에서 "그 턴엔 이 도구 외엔 낼 수 있는 답이 없다"는
  구조적 보장이라 실패 확률이 이론적으로 0에 가깝다 - `classify_case()`를 LLM 대신
  코드로 뺀 것과 같은 종류의 해법(확률적 컴포넌트에 안전-critical한 결정을 맡기지
  않는다).
- **트레이드오프**: 강제된 턴에는 LLM이 다른 도구(예: 그 턴에 동시에 필요할 수 있는
  record_case_facts)를 같이 호출할 수 없다 - 지금 범위(Step1→2 전환 시점)에선 다른
  동시 호출이 필요한 경우가 없어 문제가 안 되지만, 나중에 이 패턴을 다른 지점에
  적용할 땐 "그 턴에 정말 이 도구 하나만 필요한가"를 매번 확인해야 한다.
- **유형**: 기술(엔지니어링)적(API 레벨 구조적 보장) — guard_node(사후 검증)에 이어
  "애초에 스킵을 불가능하게 만드는" 사전 예방 계층이 하나 더 생긴 것.

## 5. 알려진 한계 및 다음 우선순위 (2026-07-31 기준)

`docs/phase1_roadmap.md`에 이미 기록된 항목 + 이후 세션에서 추가로 확인된 항목:

- 건폐율ᆞ용적률의 도로폭 완화 조항 미반영
- 복합 행위 케이스(증축+용도변경 동시 발생) 미지원 — `act_type`이 단일 필드라 표현 불가
- guard 인용 검증의 최신성 창 문제(4-3 참고) — 의도적 보류 중
- 부모-자식 청킹을 LangChain `ParentDocumentRetriever`로 교체 예정(동작 동일 유지, 유지보수성만 개선 목적)
- guard 체크 커버리지 불균등 — 실측 사고 기반으로만 좁게 만들어져, 아직 안 걸린 유사
  사고가 다른 도메인/표현에 남아있을 가능성(예: "착공"ᆞ"감리" 등 다른 표현으로 Step2를
  RAG 없이 설명하는 경우는 미포착)
- 긴 대화에서 tool-calling 저하 문제 — 4-9 참고. 컨텍스트 트리밍은 효과 미입증으로
  롤백했고, `tool_choice` 강제로 Step1→2 전환 지점 한 곳은 구조적으로 해결됨. 다만
  이건 딱 그 지점만 좁게 고친 것 — 비슷한 "지시는 있는데 강제는 안 되는" 다른
  전환 지점(예: 다른 도메인의 유사 넛지)이 더 있는지는 아직 전수 조사 안 함
