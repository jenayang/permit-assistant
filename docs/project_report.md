## 1. 프로젝트 개요

**무엇을 만들었나**: 서울시 카페ᆞ음식점 등 소규모 창업의 전체 여정(행위 유형 확인 →
건축 인허가 → 공사 → 식품위생ᆞ소방ᆞ간판ᆞ사업자등록ᆞ위생교육 → 오픈 준비)을 안내하는
LangGraph 기반 RAG 챗봇. 시작은 "서울시 건축 인허가 챗봇"이었고, 개발 중 스코프가
"창업 로드맵 어시스턴트"로 확장됐다.

**핵심 설계 원칙** (전 기간에 걸쳐 일관되게 적용됨):
- 허가/신고처럼 법령상 **객관적 기준으로 정해지는 판정은 LLM이 아니라 코드가 결정론적으로
  계산**한다. LLM은 판정 결과를 사용자에게 설명하는 역할만 맡는다.
- **"프롬프트 지시만으로는 안정성을 못 담보한다"**는 게 여러 차례 실측으로 확인되어,
  안전-critical한 지점은 전부 그래프 레벨(코드)에서 사후 검증하는 구조(`guard_node`)로
  옮겼다.
- 인프라를 먼저 일반화하지 않고, **콘텐츠(도메인)를 하나 완성해보고 반복되는 패턴이
  보이면 그때 리팩터**한다(2026-07-24 dev log에 명시된 원칙 — 실제로 도메인 3개째에서
  `DOMAIN_CONFIGS` 레지스트리로 리팩터됨).

## 4. 주요 Blocker 딥다이브

각 항목: 문제 → 검토한 대안 → 선택 이유 → 결과 → 트레이드오프 → 유형.

### 4-1. 허가/신고 판정을 LLM에 맡길 것인가, 코드로 뺄 것인가

- **문제**: 초기엔 "허가 대상인가요, 신고 대상인가요?"를 사용자에게 직접 묻거나 LLM이
  스스로 판단하게 했는데, 이건 애초에 사용자가 알 수 없는(법령상 정해지는) 값을 되묻는
  셈이었고, LLM이 계산을 틀리는 사례도 있었다.
- **검토한 대안**: (a) 프롬프트에 판정 기준을 상세히 서술하고 LLM 재량에 맡김, (b) 파이썬
  함수로 결정론적 계산 후 LLM은 설명만 담당.
- **선택 이유**: 법적 판정은 안전-critical하고 LLM의 확률적 오류를 허용할 수 없음.
- **결과**: `classify_case()` 등 6종 규칙 엔진 도입(허가/신고/기재변경, 식품위생, 소방,
  간판). 25개 경계값 회귀 테스트(`test_permit_classify.py`) 전부 통과.
- **트레이드오프**: 새 법령 개정이나 새로운 행위 유형이 생기면 규칙(if/elif) 자체를
  코드로 고쳐야 함 - 숫자만 바뀌는 개정은 YAML 분리로 흡수했지만, 조건 구조가 바뀌는
  개정은 여전히 코드 수정이 필요.
- **유형**: 기능적(정확한 판정이라는 사용자 가치) + 기술적(결정론적 로직 설계 결정).

### 4-2. 대화 상태 영속성 — 언제, 왜 지금 했는가

- **문제**: `InMemorySaver`라 서버가 재시작될 때마다 대화ᆞ판정 상태가 전부 소실.
- **검토한 대안**: (a) 뒤로 미루고 다른 기능부터 확장, (b) 지금 바로 DB 기반으로 전환.
- **선택 이유**: dev_log(07-24)에 명시 — "나머지 기능이 '세션 간 이어짐'으로 의미가
  있으려면 선행 필요"라는 원칙으로 다른 도메인 확장보다 먼저 처리.
- **결과**: `SqliteSaver`(`chroma_db/checkpoints.sqlite`)로 전환, 완전히 새 프로세스로
  재기동해도 같은 `user_id`의 대화ᆞ판정 결과가 유지되는 것을 확인.
- **트레이드오프**: 체크포인터가 상태를 msgpack으로 직렬화하는데 `PermitResult`(커스텀
  Pydantic 모델)가 기본 직렬화기에 등록 안 된 타입이라 경고가 발생 — 전체 허용 대신
  이 타입 하나만 명시적으로 허용 목록에 등록해서 해결(불필요한 타입까지 역직렬화
  허용하지 않도록 범위를 좁힘).
- **유형**: 기술(엔지니어링)적.

### 4-3. 프롬프트 지시의 한계 → `guard_node` 도입 (가장 중요한 전환점)

- **문제**: dev_log(07-24)에서 이미 "시스템 프롬프트에 지시를 강화했는데도 시설군 누락이
  재현된다 - 근본적으로는 LLM 신뢰성 이슈"라고 기록. 2026-07-26 세션에서는 판정 직후
  LLM이 여러 단계를 한 메시지에 몰아 공개하고, 사용자가 범위를 명시해도 무시하는 사고가
  실측으로 재현됨.
- **검토한 대안**: (a) 시스템 프롬프트를 계속 더 길게/강하게 작성, (b) 그래프 레벨에서
  자유 텍스트 답변을 사후 검증하는 노드 추가.
- **선택 이유**: "프롬프트 지시만으로는 못 막는다"가 반복적으로 실측 확인됨 — `classify_case`를
  코드로 뺀 것과 같은 논리를 대화 품질 검증에도 적용.
- **결과**: `guard_node` 도입 후 위반 체크가 2개(07-26) → 5개(07-28) → 6개(07-29)로
  계속 확장. 같은 턴 최대 1회 재시도로 무한 루프 방지.
- **트레이드오프**: 매 턴 정규식 기반 검증 오버헤드(경미), 위반 감지 시 응답 지연 +LLM
  재호출 1회. 그리고 이 프로젝트의 "실측 기반으로만 좁게 고친다" 원칙 때문에 **체크
  커버리지가 의도적으로 불균등** — 예를 들어 인용 검증(체크②)은 "대화 전체에 검색이
  한 번이라도 있었는지"만 보고 최신성은 안 따져서, 훨씬 이전 턴의 근거로 나중 턴의
  무관한 인용까지 통과되는 한계가 `phase1_roadmap.md`에 알려진 한계로 명시적으로
  남아있다(2026-07-29 기준 미해결, 의도적 보류).
- **유형**: 기술(엔지니어링)적 인프라, 사용자 체감 효과는 기능적(답변 신뢰성).

### 4-4. 도메인이 늘어날수록 배선이 꼬임 → `DOMAIN_CONFIGS` 레지스트리 리팩터

- **문제**: 판정 도메인이 허가 하나일 땐 괜찮았지만, 식품위생(2번째)ᆞ소방(3번째)까지
  늘면서 `classify_node`/`route_after_tools`에 도메인별 분기가 계속 늘어나는 구조가 됨.
- **검토한 대안**: (a) 도메인이 늘 때마다 if문 계속 추가, (b) 공통 인터페이스로 추상화.
- **선택 이유**: dev_log(07-24)에서 이미 "Rule Registry 분리는 세 번째 도메인이 생기면
  판단한다"고 조건을 미리 정해둠 — 실제로 3번째 도메인(소방) 추가 시점에 리팩터 실행.
  "인프라를 먼저 일반화하지 않는다"는 원칙의 실제 적용 사례.
- **결과**: 이후 4번째 도메인(간판) 추가는 그래프 배선 코드를 전혀 안 건드리고
  `DOMAIN_CONFIGS` 목록에 한 줄만 추가해서 완료.
- **트레이드오프**: 없음에 가까움(순수 개선) — 다만 각 도메인의 `classify_fn`이 라우팅
  판단(`route_after_tools`)과 실제 처리(`classify_node`) 두 곳에서 각각 한 번씩,
  총 두 번 호출되는 약간의 중복 계산이 생김(순수 함수라 비용은 무시할 수준).
- **유형**: 순수 기술(엔지니어링)적 — 사용자에게 보이는 변화 없음, 유지보수성만 개선.

### 4-5. 정적 하드코딩 콘텐츠 vs RAG 검색 — 언제 전환하는가

- **문제**: 사업자등록ᆞ위생교육ᆞ공사ᆞ4대보험 안내는 처음엔 관련 법령(부가가치세법,
  4대보험 관련법 등)이 인덱스에 없어서 원문 대조 후 정적 텍스트로 하드코딩했었다.
- **검토한 대안**: (a) 계속 정적 유지(법 개정 시 수동 재대조 필요), (b) 관련 법령을
  새로 확보ᆞ인덱싱해서 RAG로 전환.
- **선택 이유**: 법령을 실제로 추가ᆞ재인덱싱한 뒤 "정적 콘텐츠 vs RAG 비교 검증"을
  수행해, RAG가 정적 콘텐츠와 동일하거나 더 상세한 결론에 정확히 도달하는 걸 확인한
  뒤에만 전환 — 검증 없이 먼저 바꾸지 않음.
- **결과**: 4개 도메인 전부 RAG 전환 완료. 법이 개정되면 재인덱싱만 하면 자동 반영되고,
  원문을 다시 손으로 대조할 필요가 없어짐.
- **트레이드오프**: RAG는 검색 실패ᆞ환각 위험이 원천적으로 존재(정적 텍스트는 그
  위험이 없음), 매 호출마다 임베딩ᆞ검색 비용 발생. 법령 근거가 아예 없는 순수 실무
  체크리스트(인테리어ᆞ장비 설치, 영업 시작 항목)는 검색할 조항 자체가 없어 지금도
  의도적으로 정적 텍스트로 남겨둠 — "전환 가능한 것만 전환"이 원칙.
- **유형**: 기술적(검색 인프라 전환) + 기능적(법 개정 자동 반영이라는 사용자 가치).

### 4-8. "왜?" 설명이 용도변경에만 있던 비대칭 해소 (2026-07-29)

- **검토한 대안**: (a) 용도변경만 계속 특별 취급, (b) 같은 패턴을 전체 act_type으로
  일반화.
- **선택 이유**: 사용자가 "설명에 항상 근거가 붙었으면 좋겠다"고 요청, 기존 패턴이

  (숫자만 바뀌는 개정은 `get_thresholds()` 공유로 안전).
- **유형**: 기능적(설명 품질ᆞ신뢰도) — 기존 검증된 엔지니어링 패턴의 재사용.

### 4-9. 긴 대화에서 tool-calling 저하 — 컨텍스트 트리밍 시도 후 롤백 (2026-07-30~31)

- **문제**: 4-6에서 guard로 사후 방어는 추가했지만, 근본 원인(왜 대화가 길어지면
  LLM이 도구 호출을 덜 하는가) 자체는 안 건드린 상태였다. 다른 오픈소스(`selltrat`)를
  비교 검토했으나 멀티턴 에이전트 루프 자체가 없는 스캐폴드 단계라 참고할 게 없었고,
  업계에서 "lost in the middle"(긴 컨텍스트일수록 초반 지시의 영향력이 옅어지는 현상)로
  알려진 문제로 판단.
- **검토한 대안**: (a) 컨텍스트 트리밍 — 오래된 턴의 tool_call/ToolMessage 쌍을 LLM에
  보내는 사본에서만 제거(state 원본은 보존), (b) `tool_choice` 강제 — 특정 조건에서
  LLM이 도구 호출을 건너뛸 수 없게 API 레벨에서 강제.
- **선택 이유(1차 시도, a)**: 판정 결과ᆞ사실은 이미 `case_facts`/`permit_result` 등
  별도 state 채널에 보존되어 있어, 오래된 원본 tool 메시지를 LLM 컨텍스트에 계속 들고
  있을 필요가 없다고 보고 상대적으로 구현 비용이 낮은 (a)부터 시도.
- **구현**: `_trim_tool_noise()` — 최근 4턴 이전은 tool_call/ToolMessage 쌍을 제거하고
  HumanMessage+최종 텍스트만 남김. 단위 테스트 5개 전부 통과(쌍 제거 정확성ᆞ최근 턴
  보존ᆞorphan tool_call 없음ᆞ원본 불변 등 검증됨).
  **A/B 실험 결과**: 실제 세션(5db53ccb)을 재구성해 트리밍 ON(LLM 전달 메시지 29개)ᆞ
  OFF(51개) 두 조건으로 실제 Gemini를 호출해 비교했으나, **두 조건 모두
  `get_construction_guide`를 정상 호출** — 차이를 재현하지 못함. 대화 턴을 14턴까지
  늘려도 동일.
- **결론ᆞ롤백 이유**: 원 사고(turn 44)가 "길이에 비례해 확실히 나빠지는 현상"이라기보다
  LLM의 확률적 변동(가끔 실수)에 더 가까울 가능성이 있다고 판단 — 트리밍 자체는
  부작용 없이 토큰을 최대 43% 줄이는 효과는 확인했지만, "이 버그를 고쳤다"는 인과
  관계를 증명하지 못해 롤백했다. 실질적인 방어선은 이 트리밍보다 4-6의 guard 체크일
  가능성이 높다는 게 이번 실험의 핵심 교훈.
- **트레이드오프**: 실험 자체가 실제 Gemini API 호출(무료 티어 할당량)을 소모함 - 단발
  A/B는 LLM의 확률적 특성상 증거력이 약하다는 방법론적 한계도 확인.
- **유형**: 기술(엔지니어링)적 실험 — 이번엔 명확한 결과 없이 "가설 기각"으로 끝났고,
  그 자체를 기록해두는 것도 과정의 일부로 남긴다.

**→ 2차 시도(대안 b) — `tool_choice` 강제, 성공**: `langchain_google_genai`ᆞ
`langchain_cerebras`의 `bind_tools(tool_choice=...)`가 특정 함수명을 강제 호출시키는
기능을 실제로 지원함을 소스 코드로 확인(둘 다 문자열 함수명 → 내부적으로 정규화).
`_should_force_construction_guide()`를 추가해, "Step1 끝ᆞconstruction_guide
미호출ᆞ직전 AI 메시지가 방금 Step2를 제안했고 사용자가 그에 응답하는 턴"으로만
강제 범위를 좁혔다(조건 없이 전체 구간에 강제하면 그 구간에 사용자가 완전히 다른
주제를 물어봐도 매번 공사 안내로 강제 전환되는 부작용이 생기기 때문). 이 조건일 때만
`llm.bind_tools(TOOLS, tool_choice="get_construction_guide")`로 그 턴만 새로
바인딩해서 호출한다(평소 경로의 캐싱된 `llm_with_tools`는 안 건드림).
**라이브 검증 결과**: 트리밍 실험과 똑같이 재구성한 시나리오로 실제 Gemini를
호출한 결과, `tool_calls: [('get_construction_guide', {})]` — 다른 텍스트나 다른
도구 호출 없이 정확히 그 도구만 호출됨을 확인. 단위 테스트 5개 추가(강제 대상
판별 로직 - 제안 직후 응답ᆞ이미 호출됨ᆞStep1 미완료ᆞ무관한 주제ᆞ직전 메시지가
사람이 아닌 경우), 전체 스위트 113개 통과.
- **1차(트리밍)와의 차이**: 트리밍은 "LLM이 지시를 더 잘 따르길 기대"하는 확률적
  개선이었던 반면, 이건 API 레벨에서 "그 턴엔 이 도구 외엔 낼 수 있는 답이 없다"는
  구조적 보장이라 실패 확률이 이론적으로 0에 가깝다 - `classify_case()`를 LLM 대신
  코드로 뺀 것과 같은 종류의 해법(확률적 컴포넌트에 안전-critical한 결정을 맡기지
  않는다).
- **트레이드오프**: 강제된 턴에는 LLM이 다른 도구(예: 그 턴에 동시에 필요할 수 있는
  record_case_facts)를 같이 호출할 수 없다 - 지금 범위(Step1→2 전환 시점)에선 다른
  동시 호출이 필요한 경우가 없어 문제가 안 되지만, 나중에 이 패턴을 다른 지점에
  적용할 땐 "그 턴에 정말 이 도구 하나만 필요한가"를 매번 확인해야 한다.
- **유형**: 기술(엔지니어링)적(API 레벨 구조적 보장) — guard_node(사후 검증)에 이어
  "애초에 스킵을 불가능하게 만드는" 사전 예방 계층이 하나 더 생긴 것.

### 4-10. 컨텍스트 예산 실측 — 시스템 프롬프트ᆞ도구 설명ᆞ가이드 도구 토큰 감사 (2026-07-31)

  검토한 적이 없었다. 실제 숫자로 확인이 필요했다.

  "가이드" 도구(`get_construction_guide`ᆞ`get_business_registration_guide`ᆞ
  `get_hygiene_education_guide`ᆞ`get_opening_checklist`)를 실제로 호출해 반환값을
  직접 토큰화했다.
- **결과(수정 전 기준)**:

  |---|---|
  | `SYSTEM_PROMPT` | 8,761 |
  | 도구 15개 설명(description) 합계 | 7,614 |

    여유가 큼.

    폴백의 하드 한도에 근접ᆞ초과할 수 있는 실측 근거. 게다가 폴백이 걸리는 조건

- **조치 1 — 프롬프트/도구 설명 속 "개발자 인시던트 일지" 제거**: `SYSTEM_PROMPT`ᆞ

- **조치 2(완료, 2026-08-01) — 시스템 프롬프트와 도구 설명의 중복 제거**: 도구는

  재판정ᆞ병행 질문 안내 - 도구 docstring에 없는 대화 흐름 로직)은 그대로

  자동조회부터")은 어느 한 도구의 description에도 넣을 수 없는 교차-도구
  로직이라 그대로 남겼다. **효과(실측)**: `SYSTEM_PROMPT` 8,477→7,570 토큰

### 4-11. 조건부 프롬프트 조립 — 도메인 블록을 상태에 따라 켜고 끄기 (2026-08-01)

- **문제 제기**: 4-10에서 인시던트 서사 제거(-284)ᆞ도구 설명 중복 제거(-907)를
  했지만, 남은 7,570 토큰은 "규칙 본문"이라 더 줄일 여지가 없어 보였다. 그런데
  절별로 쪼개 재보니 **`## 1. 정보 수집` 하나가 3,307 토큰으로 전체의 44%**였고,
  그 안에 건축ᆞ식품ᆞ소방ᆞ간판ᆞ진행률 수집 규칙이 전부 섞여 있었다 — 간판만
  물어보는 턴에도 식품ᆞ소방 규칙을 매 턴 다 읽히는 구조였다는 뜻이다.
  | 절 | 토큰 | 비중 |
  |---|---|---|

  | `## 3. 답변 작성` | 2,299 | 30% |

  Planner가 라우팅"(각 에이전트 프롬프트 100~300토큰)이었다. 방향은 맞지만
  그건 Phase 5(Planner)이고, 대화형 UX와의 충돌 우려로 이미 의도적으로 보류한
  결정이다. 게다가 컨텍스트 트리밍(4-9)도 "길이 때문일 것"이라는 가설로 구현까지
  갔다가 실측에서 반증돼 롤백한 전례가 있다. 그래서 **그래프 구조 변경 0ᆞ새 LLM
  호출 0ᆞ되돌리기 쉬운** 중간 단계를 먼저 택했다: 이미 매 턴 동적으로 조립되던
  `permit_phase_directive`ᆞ`_roadmap_status_summary`와 같은 메커니즘으로,
  `## 1`ᆞ`## 3`의 도메인 블록도 상태에 따라 켜고 끈다.
- **구현**: `SYSTEM_PROMPT` 단일 상수를 블록 상수 16개로 쪼개고
  `build_system_prompt(state)`가 매 턴 조립한다(`agent.py`). 블록 점등 조건은
  **느슨한 OR** — ① 그 도메인이 이미 상태에 살아있음(facts/result 기록됨)
  ② **대화 전체의** 유저 발화 어딘가에 그 도메인 키워드가 있음. 둘 다 "한 번
  켜지면 대화가 끝날 때까지 유지"되는 성질이라 블록이 턴마다 깜빡이지 않는다.
  조건을 느슨하게 잡은 건 의도적이다 — **꺼야 할 블록을
  켜두는 비용은 토큰 몇 백이지만, 켜야 할 블록을 끄면 그 도메인의 판정 자체가
  조용히 실패하는 비대칭 리스크**가 있기 때문. 예외로 소방은 `food_result`가
  있으면 무조건 켠다("식품접객업이면 소방도 함께 판정하라"는 선제 규칙을 잃으면
  `guard_node`의 소방 미판정 체크에 계속 걸린다).

- **세 번째 지점 — 키워드 점등이 멀티턴에서 꺼지던 버그(사용자 지적으로 발견)**:

### 4-12. tool-calling 스킵 원인 규명 — 프롬프트가 아니라 도구 선택의 문제였다 (2026-08-02)

프로젝트 최대 미해결 과제였다(4-9에서 컨텍스트 트리밍 시도 후 반증ᆞ롤백, 이후
`guard_node` 사후 검증과 `tool_choice` 좁은 강제로 각각 부분 완화만 해둔 상태).

- **측정 설계를 먼저 고쳤다**: 지금까지는 `pipeline.query()`로 재고 있었는데, 그건
  한 번 부르면 도구 루프ᆞ`classify`ᆞ`guard` 재시도까지 다 도는 경로라 (a) 시행당
  LLM 콜을 여러 번 쓰고(무료 티어 일 20회를 금방 소진) (b) **guard 재시도가 두 번째
  시도에서 도구를 부르면 마치 성공한 것처럼 보인다**. 실제로 2026-08-01에 "어제는
  실패했는데 오늘은 성공"으로 보였던 게 이 착시였다. `llm.bind_tools(...).invoke()`를
  직접 1회만 호출하도록 바꿔 **시행당 정확히 1콜**로 격리했다.
- **조건별 실측(각 3회 반복, 전부 동일 = 결정론적)**:

  | 입력 | 15개 도구(운영과 동일) | 관련 도구 3개만 | `tool_choice` 강제 |
  |---|---|---|---|
  | "…벽면에 붙이는 간판…신고해야 하나요?" | **0/3** | 3/3 | 3/3 |
  | "카페 창업하려고요." | **0/3** | **0/3** | 3/3 |

- **가설별 결론**:
  - **"모델이 도구를 필수가 아니라 권장으로 다룬다" — 확인.** `tool_choice` 강제는
    두 입력 모두 100%. 프롬프트에 "반드시 기록하라"를 여러 번 강화해도 안 고쳐지던
    이유가 이것이다.
  - **"도구 수가 선택을 흐린다" — 부분 확인.** signage는 15개→3개로 줄이자 0%→100%.
    다만 food는 3개로 줄여도 0%라 도구 수만으로는 설명되지 않는다.
  - **"질문형이면 답변 모드로 들어간다" — 기각.** 스킵된 두 입력 중 "카페
    창업하려고요."는 서술형이다. 어미와 무관하다.
  - **"긴 대화라서" — 재차 기각.** 전부 새 세션 첫 턴에서 재현됐다. 4-9의 트리밍
    실험이 효과를 못 보인 이유가 이걸로 설명된다 — 애초에 길이가 원인이 아니었다.
  - **결정론적이다.** 6개 조건 전부 3회 반복이 완전히 동일했다. 랜덤이 아니라
    재현 가능한 현상이라 회귀 테스트로 고정할 수 있다.
- **조치 — `tool_choice` 강제를 모든 도메인으로 일반화**: `get_construction_guide`
  한 지점에만 좁게 쓰던 방식(`_should_force_construction_guide`)을 `_forced_record_tool`
  로 확장했다. 유저가 이번 턴에 어떤 도메인을 꺼냈는데(키워드) 그 도메인 사실이 아직
  하나도 없으면 그 도메인의 `record_*`를 API 레벨에서 강제한다. `DOMAIN_CONFIGS`에
  `record_tool`ᆞ`keywords`를 추가해, 도메인이 늘어도 그 목록 한 줄만 고치면 되도록
  기존 레지스트리 패턴(4-4)을 그대로 따랐다.
  강제 범위를 좁게 유지하는 세 조건: ① facts가 완전히 비었을 때만(도메인당 사실상
  첫 기록 한 번) ② 이번 턴에 그 도구가 아직 안 불렸을 때만(모델이 전부 None으로
  채워 보내면 facts가 계속 비어 무한 강제가 되는 걸 끊음) ③ 정의를 묻는 질문
  ("건폐율이 뭐야")은 제외(기록할 사실이 없음).
- **의미**: 이 문제를 "프롬프트를 더 잘 쓰면 해결된다"고 보고 여러 번 프롬프트를
  강화했지만, 실측은 **프롬프트 층위의 문제가 아니라 도구 선택 층위의 문제**임을
  보여준다. `guard_node`(사후 교정)와 `tool_choice`(사전 강제)는 둘 다 필요하다 —
  전자는 이미 벌어진 누락을 잡고, 후자는 애초에 벌어지지 않게 한다.
- **강제 범위의 경계(2026-08-02 합의)**: **기록(`record_*`)은 강제, 검색
  (`search_regulations`ᆞ`lookup_land_zone`ᆞ`lookup_building_ledger`)은 모델 판단.**
  검색까지 강제하면 "언제 검색이 필요한가"라는 맥락 의존적 판단까지 규칙으로 못 박게
  되어 모델의 판단권이 과도하게 줄어든다. 기록은 반대다 — 유저가 이미 말한 사실을
  적는 일이라 판단의 여지가 없고, 안 적으면 판정이 영영 안 되는 게 확정적이다.
  예외는 `get_construction_guide` 하나인데, 그건 검색 전략이 아니라 "Step1→2 전환을
  그 턴에 반드시 짚어야 한다"는 로드맵 진행 규칙이라 성격이 다르다. 이 경계는
  테스트로 고정해뒀다(`test_only_record_tools_are_forceable`).
- **강제 판단 로깅(같은 날 추가)**: 강제가 실제로 얼마나 자주 필요한지, 강제 후에
  무엇이 추출됐는지를 나중에 집계할 수 있도록 구조화된 로그를 남긴다. 이 프로젝트는
  실측으로 방향을 정해왔는데(4-9 트리밍 반증, 4-12 원인 규명) 정작 강제 자체에 대한
  데이터가 없었다.
  ```
  [FORCED_TOOL] domain=signage tool=record_signage_facts reason=no_facts trigger='간판'
  [FORCED_TOOL_RESULT] tool=record_signage_facts called=True args={'sign_type': '벽면이용간판'}
  ```
  두 줄을 나눠 찍는 게 핵심이다 — `called=False`면 tool_choice 강제조차 안 먹혔다는
  뜻이라 즉시 조사 대상이고, `called=True`인데 `args={}`면 "호출은 됐지만 추출은
  실패"라 **호출률과 추출 품질을 분리해서** 볼 수 있다.
- **남는 한계**: 강제는 "유저가 도메인 키워드를 쓴 턴"에만 걸린다. 키워드 없이
  사실만 흘리는 발화(예: "3층이고 200제곱미터예요")는 여전히 모델 재량이다.
  또 강제된 호출에 모델이 값을 제대로 채우는지까지는 보장하지 못한다(호출 자체만
  보장) — 이게 다음 과제이고, 위 로그가 그 측정의 입력이 된다. 회귀 테스트 9개
  (`tests/test_forced_record.py`)로 강제가 걸리는 자리와 안 걸리는 자리를 양방향으로
  고정해뒀다.

### 4-14. 컨텍스트 예산 관측 + 초과 시 우아한 처리 (2026-08-02)

- **문제**: 4-13으로 여유가 30%까지 늘었지만, **초과 시 처리가 여전히 없었다.**
  넘으면 프로바이더 원본 에러(영문)가 그대로 500으로 나가 사용자는 무엇을 해야
  할지 알 수 없었다. 게다가 실제 대화가 얼마나 컨텍스트를 쓰는지 **운영 데이터가
  전혀 없어서**, 트리밍ᆞ요약을 도입할지 말지를 추정으로만 판단하고 있었다.
- **선택**: 큰 설계(트리밍ᆞ상태 요약)를 지금 넣지 않고 **관측 + 안전망**만 뒀다.
  이 프로젝트에서 근거 없이 구조를 바꿨다가 롤백한 전례가 있고(4-9), 반대로 로깅을
  먼저 깔아 실측으로 판단한 방식은 계속 좋은 결과를 냈다(4-12).
- **추정 방식**: 한국어 법령ᆞ대화 텍스트를 실측하니 cl100k 기준 **1.02 문자/토큰**으로
  꽤 일정해서(시스템 프롬프트 1.18, 가이드ᆞ검색 결과ᆞ대화문 모두 1.02), 문자 수를
  그대로 토큰 수로 본다 — 약 2% 과대추정이라 가드 입장에선 안전한 방향이다.
  `tiktoken`을 쓰지 않은 이유: ① 직접 선언한 의존성이 아니라 전이 의존성이고
  ② cl100k는 Gemini/Gemma의 토크나이저가 아니라 어차피 근사치라, 정밀도를 위해
  의존성을 늘릴 이유가 없다. 도구 스키마(설명+args)는 매 호출 전송되지만 messages엔
  없으므로 따로 더한다(빼먹으면 1만 토큰 가까이 과소평가된다).
- **구현**:
  - `estimate_tokens()` + `_log_context_usage()` — 매 LLM 호출마다 사용량을 남긴다.
    폴백 여부에 따라 한도가 달라지므로 모델별로 계산한다.
    ```
    [CONTEXT] model=gemini est=21,340 limit=1,048,576 pct=2%
    [CONTEXT] model=cerebras est=98,500 limit=131,072 pct=75% - 한도 근접
    ```
    `CONTEXT_WARN_RATIO`(0.75)를 넘으면 WARNING으로 올린다. **차단은 하지 않는다** —
    지금 목적은 막는 게 아니라 "실제로 얼마나 자주 위험 구간에 가는지" 데이터를
    쌓는 것이다.
  - `ContextOverflowError` + `_is_context_overflow_error()` — 프로바이더 문구가
    제각각이라 부분 문자열로 넓게 잡는다(잘못 잡아도 결과는 "더 친절한 안내"라
    안전한 방향). 할당량 초과(429)와는 대응이 완전히 달라서(전자는 폴백 전환, 후자는
    새 대화 안내) 서로 오인하지 않는지 테스트로 고정했다.
  - `api.py` — 이 타입만 골라 **413 + 행동 가능한 한국어 안내**로 바꾼다. 판정 결과는
    이미 상태에 남아 있으므로 "새 대화를 시작해도 처음부터 다시 할 필요 없다"는 점을
    함께 안내한다.
- **후속 — 자동 절삭 도입(같은 날)**: 처음엔 "로그를 쌓고 판단하자"고 미뤘는데,
  사용자 지적으로 방향을 바꿨다 — **"새 대화를 시작하세요"는 기능이 아니라 실패
  처리**이고, 자동으로 끊어주는 게 맞다. 다시 보니 롤백된 트리밍(4-9)과 지금
  제안은 다른 물건이었다:

  | | 롤백된 것(4-9) | 지금 도입한 것 |
  |---|---|---|
  | 트리거 | **항상**(최근 4턴만 유지) | 한도의 80% 넘을 때만 |
  | 목적 | tool-calling 개선(증명 실패) | 하드 에러 방지(원인 명확) |
  | 평소 영향 | 매 턴 동작 | **아예 안 켜짐**(실제 대화 2~3%) |

  즉 "근거 없이 되돌린 걸 또 넣는" 게 아니라, 트리거와 목적이 다른 별개 조치다.
- **구현 선택 세 가지**:
  1. **예산 기준 트리거**(`CONTEXT_TRIM_RATIO=0.8`) — 짧은 대화의 멀쩡한 맥락을
     매번 버리지 않기 위해. 실제 대화가 2~3%라 평소엔 죽어 있는 코드다.
  2. **LLM에 보내는 사본만 절삭, `state["messages"]`는 보존** — `guard_node`가
     메시지 이력을 스캔해 검색 여부(`_has_grounding_search`)ᆞ공사 안내 호출 여부
     (`_construction_guide_shown`)를 판정하기 때문이다. 원본을 지우면 "검색 안
     했다"고 오판해 **없는 위반을 만들어낸다**. 체크포인터에도 전체 이력이 남는다.
  3. **직접 구현 대신 `langchain_core.messages.trim_messages`** — 유효한 이력
     형태(HumanMessage로 시작)와 tool_call/ToolMessage 짝 맞추기를 알아서 한다.
     짝이 깨지면 프로바이더가 400을 뱉는데 직접 관리하면 버그가 나기 쉽다.
- **이 구조에서 절삭이 특히 안전한 이유**: 판정 결과ᆞ사실이 메시지가 아니라 별도
  상태 채널(`case_facts`ᆞ`permit_result` 등)에 있고, `_roadmap_status_summary`가
  매 턴 현황을 다시 주입한다. 오래된 메시지를 빼도 "지금까지 뭐가 확정됐는지"는
  그대로 전달된다 — 일반 챗봇이라면 위험한 조치가 여기선 상대적으로 안전하다.
- **효과(실측)**: 50개 메시지 215,140 토큰(초과 확정) → 20개 95,010 토큰
  (한도의 72%). 최근 대화는 보존되고, 주 모델(약 100만 토큰)에선 같은 이력이
  안 잘린다.
- **요약(summarization)은 넣지 않았다**: 턴당 LLM 호출이 추가되는 비용도 있지만,
  더 중요한 건 **법령 근거를 요약하면 조문 번호가 뭉개진다**는 점이다. 자르는 건
  "없어지는" 거고 요약은 "틀리게 남는" 거라, 근거 정확성이 핵심인 이 프로젝트에선
  성격이 다르다. 절삭으로도 맥락이 실제로 끊기는 게 관측되면 그때 재검토한다.
- **다음 판단 기준**: `[CONTEXT]` 절삭 로그가 실제로 자주 찍히면 그때 요약을
  검토한다. 지금은 절삭이 발동하는 것 자체가 드물 것으로 예상된다.
- 회귀 테스트 8개(`tests/test_context_guard.py`) — 추정이 메시지량ᆞ도구 스키마ᆞ
  tool_calls args를 반영하는지, 한국어에서 과소추정하지 않는지, 프로바이더별 에러
  문구를 잡는지, 할당량 에러와 혼동하지 않는지.
