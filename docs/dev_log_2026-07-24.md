# 개발 일지 — 2026-07-24: "건축 인허가 챗봇" → "창업 로드맵 챗봇" 확장 1차

## 오늘의 배경

기존 챗봇은 "카페를 열려면 지금 뭐부터 해야 해?"라는 사용자의 진짜 질문에 답하기엔
건축 인허가 판정(Step 0~2)까지만 다루고 있었다. 창업 전체 과정(사업자등록ᆞ
식품위생 영업신고ᆞ소방ᆞ간판신고ᆞ오픈준비)까지 로드맵을 넓히기 위한 구조를
논의하고, 그중 가장 우선순위가 높은 조각부터 실제로 구현했다.

## 확정한 개발 순서

여러 구조안(Rule Registry 선분리, Planner Agent 멀티에이전트 등)을 검토한 뒤,
"인프라를 먼저 일반화하지 말고 콘텐츠부터 하나 완성해보고 판단한다"는 원칙으로
아래 순서에 합의했다.

1. **Project State(DB 영속화)** — 나머지 기능이 "세션 간 이어짐"으로 의미가
   있으려면 선행 필요
2. **두 번째 도메인(식품위생법 영업신고) 실제 구현** — 데이터가 이미 있어 가장
   저렴한 다음 스텝
3. Rule Registry 분리는 세 번째 도메인이 생기면 판단
4. Planner Agent(멀티에이전트 라우팅)는 라우팅이 실제로 복잡해지면 투자

지금까지 1~2번을 진행했다.

## 구현한 것

### 1. Project State — LangGraph 체크포인터 SQLite 전환
대화 이력ᆞ`case_facts`ᆞ`permit_result`를 담고 있던 체크포인터가 `InMemorySaver`라
서버가 재시작될 때마다 전부 소실되고 있었다. `SqliteSaver`(`chroma_db/checkpoints.sqlite`)로
교체해서, 서버를 껐다 켜도 같은 `user_id`로 대화가 이어지도록 만들었다. 완전히 새
프로세스로 같은 세션을 다시 불러와도 이전 대화ᆞ판정 결과가 유지되는 것을 확인했다.

### 2. 식품위생법 영업 판정 규칙 엔진 (Step 3b)
`classify_case`(건축)와 동일한 원칙 — 휴게음식점/일반음식점/제과점/즉석판매제조가공업
같은 영업 종류 구분은 법령상 객관적 기준(음주 허용 여부 등, 식품위생법 시행령
제21조)으로 정해지므로 LLM 판단에 맡기지 않고 파이썬 규칙(`classify_food_business`)이
결정론적으로 계산하게 만들었다. 확인해보니 식품위생법 법률ᆞ시행령ᆞ시행규칙 전부
이미 데이터/인덱스에 있어서 별도 문서 확보 없이 바로 규칙만 짜면 됐다.

건축(`permit_result`)과 나란히 `food_result`를 상태ᆞAPI 응답에 노출했고,
프론트 사이드패널에도 별도 색상 칩으로 표시되게 했다.

### 3. VWorld 용도지역 자동 조회 — 운영키 승인 후 마무리
개발 중 VWorld 지오코딩ᆞ2D데이터 API가 운영키로 승인되면서, 그동안 막혀있던
용도지역 자동 조회를 실제로 살렸다. 승인 후에도 한 번 막혔는데, 원인은 키가
아니라 서버사이드 호출에 필요한 `domain` 파라미터 누락이었다(운영키는 브라우저
Referer 대신 이 파라미터로 도메인을 검증함). 실제 응답 구조도 확인해서 용도지역명
필드(`uname`)와 레이어ID를 추정치에서 검증된 값으로 바꿨다.

## 개발 중 발견ᆞ해결한 문제

### (버그) 도구 호출이 상태에 반영 안 됨
`record_food_facts`를 새로 추가하면서, 그 결과를 상태에 반영하는 함수
(`_agent_result`)에 처리 분기를 추가하는 걸 빠뜨렸다. 도구 자체는 정상 호출되는데
`food_facts`엔 하나도 안 남아 분류가 영영 안 걸리는 문제였다 — 테스트 중 발견해서
바로 수정.

### (설계 문제) 규칙 엔진이 필요 이상으로 깐깐했음
식품 판정에 필요한 4개 사실을 전부 다 알아야만 판정하게 짰었는데, 실제로는
"베이커리로 직접 제조ᆞ판매"라는 사실 하나만 확정되면 나머지(즉석판매 여부 등)는
결과에 영향이 없다. 사용자가 실제로 3/4 정보를 줬는데도 나머지 하나를 LLM이
안 물어봤다는 이유로 계속 미분류로 남는 걸 실측으로 확인해서, 이미 확정된
사실만으로 결론이 나면 그 자리에서 바로 판정하도록(단락 평가) 구조를 고쳤다.

### (진행 중 이슈) LLM이 판정에 필요한 사실을 끝까지 기록하지 않음
가장 반복적으로 나타난 문제. 예를 들어 용도변경 케이스에서 시설군(facility group)
값을 하나만 기록하고 `act_type`이나 반대쪽 시설군을 빠뜨린 채, 마치 판정이 끝난
것처럼 텍스트로 답변해버리는 사례가 여러 번 있었다. 시스템 프롬프트에 "용도변경엔
`act_type`ᆞ양쪽 시설군이 다 있어야 판정된다"는 지시를 강화했고, 실제로 `act_type`
누락은 개선됐지만 시설군 누락은 여전히 재현되는 걸 확인했다 — 프롬프트만으로는
완전히 막기 어려운, 근본적으로는 LLM 신뢰성 이슈다. 같은 맥락에서 법령 검색
(`search_regulations`)을 아예 생략한 채 필수서류를 답변한 사례도 발견했다(근거
없이 지어낸 서류 목록이 나간 셈). 현재는 원인을 파악해서 기록해둔 상태이고,
근본 해결(예: 판정 완료 여부를 답변 전에 강제로 재검증하는 그래프 단계 추가 등)은
다음 과제로 남겨뒀다.
